# PF-02 テナントのスナップショット（運営面のデータ供給）

**系列**: PF（起票 2026-08-20 / DECISIONS #219 / #220）
**仕様**: `ui-prototypes/platform/pkplat-A-status-tenants.html` 02 / 03
**依存**: PF-01
**見積**: 2日
**ステータス**: 実装済み（2026-08-20）

## 背景
運営画面が要る数字（テナント数・施設数・客室数・スタッフ数・記録の完備率・
既定値のまま比率・入力所要時間の中央値・課金対象室数）は**全部テナントの中**にある。
リクエスト時に 16 シャードへ fan-out することは禁止されている。
**Queue コンシューマが 1 テナント 1 行のスナップショットを SHARD_00 へ書き、
運営画面はそれだけを読む**（#220）。

## やること

### `platform_tenant_snapshot`（SHARD_00）
`organizationId` × `businessDate` で 1 行。
名称・契約日・プラン・施設数・客室数・スタッフ数・完備率・既定値のまま比率・
入力所要時間の中央値・課金対象室数・状態（稼働 / 試用 / 注意 / 停止）。

**`orgShortId` を主キーにしない**（表示に使わない）。
**シャード番号を列に持たない**（architecture.md §1）。

### Queue `platform-snapshot`
- Cron で 1 日 1 回、テナントごとに 1 メッセージ。
- コンシューマは**その 1 テナントのぶんだけ** `getTenantDb()` を使って読み、
  SHARD_00 へ 1 行書く。**1 メッセージが触るテナントは 1 つ。**
- **再計算方式**（rollup と同じ / architecture.md §3）。3 回実行しても同じ。
- 集計の元は `dailyPropertyRollup` と既存の口。**タスク表を直に数えない。**

### 記録の品質の判定
プロトタイプ 03 の注記を逐語で守る。
> 判定は3指標の組み合わせです。完備率90%未満・既定値70%超・入力時間10秒未満のうち2つ以上該当で「要支援」とします。

閾値は PF-14 の「運用（変更可）」から来る。**ここでベタ書きしない。**

## やらないこと
- 個人を特定できる列（氏名・メール・端末 ID）を運営面へ渡すこと（INV-10）
- テナント横断の JOIN（読むのは 1 テナントずつ）
- シャード番号の露出

## 完了条件
- [x] コンシューマを 3 回流して結果が変わらない（冪等 / testing.md §4）
- [x] 1 メッセージが 2 つ以上のテナントに触れていない
- [x] スナップショットに個人を特定できる列が無い（走査テスト）
- [x] シャード番号が列にもレスポンスにもログにも出ない

## 作業ログ

### 2026-08-20 実装

**キューも cron も新設しない**（DECISIONS #231）
- `platform-snapshot` を作らず、**`pk-rollup-update` に `kind` で相乗り**
  （DECISIONS #140 / #160 の判断を踏襲）。どちらも「数え直して上書きする」
  再計算方式で性質が揃っている。新しいキューは 4 環境ぶんの Cloudflare
  リソース作成が要り、人間を待たせる。
- 発火も **02:00 JST の回に相乗り**（照合・写真の保持期限と同じ）。
  新しい cron 式を足すと、fallthrough より前に分岐を置き忘れた日に
  タスク生成がその時刻にも走る。

**表（SHARD_00 / migration 0032）**
- `platform_tenant_snapshot` — `organizationId` × `businessDate` で一意。
  **`orgShortId` を持たない・シャード番号の列を持たない。**
- **測った値だけを置く。** 完備率も既定値のまま比率も**列にしない** —
  件数（分子・分母）を持ち、割合は読むときに出す。分母 0 のときの扱い
  （0% なのか「まだ無い」なのか）を列の中に隠さないため。
- **判定（要支援 / 注意）を保存しない。** 閾値は PF-14 の「運用（変更可）」
  から来るので、焼き込むと**値を変えた瞬間に過去の行と食い違う。**
- `platform_operation_setting` — PF-14 の 5 項目だけ。1 行しか持たない。
  **読む関数しか作っていない**（変更は申請と承認 2 名 = PF-14 の担当）。
  行が無ければ既定値（`PLATFORM_OPERATION_DEFAULTS`）。

**判定（`packages/engine/src/tenantQuality.ts`）**
- 逐語の 2-of-3。**閾値は引数で受け取る**（ベタ書きしない）。
- ただし**完備率の 90% だけは定数**。PF-14 の「運用（変更可）」5 項目に
  無いので、編集できる設定を勝手に増やさない（プロトタイプが上限）。
- **値が無い指標を悪い側に倒さない。** 完了タスクが 0 の日・計測が無い日を
  「該当」にしない。倒すと**稼働していないテナントが全部「要支援」になる。**
- 割合は整数（切り捨て）。浮動小数点を持ち回らない。

**コンシューマ（`apps/web/src/consumers/tenantSnapshot.ts`）**
- 1 通 = 1 テナント。`lookupOrganizationId()` で解決した 1 組織の `ctx` で
  しか読まない。
- 完了タスク数は `daily_property_rollup` の施設合計。**タスク表を直に
  数えない**（走査テストで固定）。
- 中央値は SQLite に集約関数が無いので、**計測値の配列を返して純粋関数で
  出す**（`medianDurationMs()`）。1 テナント 1 日ぶんなので件数は小さい。
- 個人を渡さない: `summarizeObservationInput()` は `recordedById` を選ばない。

**検査**
- `consumers/tenantSnapshot.spec.ts`（15 件）— 3 回流して同じ SQL、
  `id` が組織と業務日から決まる、他テナントの ID がどのクエリにも出ない、
  INSERT に個人の列・シャードの語が無い、観察記録の読み取りが記録者を
  選んでいない。
- `lib/platform/snapshotDispatch.spec.ts`（8 件）— 組織ごとに 1 通、
  1 組織で落ちても止まらない、結果に組織 ID を含めない。
- `packages/engine/src/tenantQuality.spec.ts`（23 件）— 正例・負例 5 件ずつ、
  境界（ちょうど 90% / 70% / 10 秒）、閾値を引数から読むこと。
- `repositories/platform.spec.ts` に 10 件追加、`repositories.spec.ts` の
  `INVOCATIONS` に新しい 2 関数を登録（組織条件の自動検査が掛かる）。

## 申し送り
- **スナップショットを読む画面がまだ無い。** `listTenantSnapshots()` と
  `judgeTenantQuality()` は置いてあるが、呼ぶのは PF-04 / PF-05。
- **運用設定の書き込み口が無い**（PF-14 の担当）。いまは既定値のまま動く。
- `contractedOn` は `subscription.createdAt`、無ければ `organization.createdAt`。
  **契約日そのものを持つ列がテナント側に無い。** 実際の契約日と食い違う
  組織が出たら、テナント側に列を足すか PF-04 で運営が上書きする形になる。
