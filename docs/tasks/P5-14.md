## 作業ログ

### 着手前に見つかったこと — 表は空だった

`daily_property_rollup` は P0-21 が作り、施設サマリー（PK-SPEC-P0 §23.3）と
この画面（§7.1）の**唯一の出どころ**に定められていた。ところが
**行を作る経路が 1 つも存在しなかった。** `rollup-update` キューに
コンシューマが無く、投入する側も無い（P4-05 の申し送り
「rollup へはまだ投げない」）。読む口（`listPropertyRollups()`）だけがあり、
常に 0 件を返していた。

そのため P5-14 の本体は画面ではなく**書き込み側**になった。

### 入れたもの

| 層 | 追加 |
|---|---|
| schema | `inspectedTasks` / `firstPassTasks`（migration `0016`・追加のみ） |
| repositories | `listRollupsInRange` / `upsertPropertyRollup` / 材料の 3 本 |

| 画面 | `/app/org/dashboard` を単日から月次へ育てた |

### 止まらずに判断したこと

- **#131** 初回検査合格率のために rollup へ列を 2 つ足す。
  指標を落とすか列を足すかの二択で、後方互換の追加を選んだ。
- **#132** rollup に金額の列を置かない。清掃費用は発行済み請求書の明細から。
  **その月の請求書が無ければ `null`。0 円と書かない。**
- **#133** `openIssues` を業務日で絞らず現在値として持つ。
  業務日 → タイムスタンプの窓を作る手段がコードに無い（OPEN_QUESTIONS #080）。
- **#134** 集計の投入は「状態が動いたとき」に投げ、失敗を握りつぶす。
  派生データの更新で現場の操作を止めない。

### 起票した問い

- **#080** 業務日からタイムスタンプの窓を作る手段が無い
- **#081** 自社清掃の組織では「清掃費用合計」を出せない
- **#082** 忘れ物・設備不具合・請求期間の PC 画面がまだ無い
  → 要対応の 4 行のうち 3 行に `[ 確認する ]` を置いていない

### やっていないこと

- **`hasRollup` を施設ごとに持たせていない。** 月の中で 1 日でも集計が
  あれば真。施設ごとの「まだ集計が無い」は出していない（月次では
  「その施設は 0 件だった」と区別する意味が薄いため）。
- **キャッシュを置いていない。** 施設セレクタ（§23.3）は 60 秒キャッシュを
  持つが、こちらは月次で開く回数が少なく、要対応の件数が古いまま見える
  ほうが害が大きい。
