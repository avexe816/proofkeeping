# PF-20 監査ログを読み取り専用で引く phase を足す

**系列**: PF（起票 2026-08-22 / オーナー指示） **依存**: なし
**見積**: 0.5 日 **ステータス**: 未着手

## 背景
運営面の障害を切り分けるには `platform_audit_log` を読む必要があるが、
**既存の読み取り専用 phase では見られない。** `staging-bootstrap.yml` の
`db-status` が出すのは表の数・`schema_version`・組織数・利用者数・施設数まで
（しかも「表の数」は 0 と出る既知の不具合 / OPEN_QUESTIONS #116）。

2026-08-21 の TOTP 登録失敗の切り分けでは、**Cloudflare Dashboard の D1
コンソールで手で `SELECT` を打つ**しかなかった（DECISIONS #250 の追記）。
実際に原因（端末の時刻ずれ系）は特定できたが、**自由に SQL を打つ運用を
常態化させたくない。**

## やること
`staging-bootstrap.yml` に読み取り専用の phase（`audit-tail` など）を足す。

- 対象は **SHARD_00 だけ**（`platform_*` はそこにしか無い）
- 出すのは **`action` / `detail` / `created_at` と件数**まで
- **`SELECT` のみ。** 書き込みの経路を持たない
- 既存の `db-status` と同じ形（`wrangler d1 execute` の読み取り）

## 出してよいもの・いけないもの
`platform_audit_log` の `detail` には **secret・TOTP・復旧コード・宛先が
入らない設計**（DECISIONS #246 / #245）。そのまま出してよい。
**ただし `detail` を丸ごと出す形にはしない** — 将来 detail に項目が
足されたとき、一緒に出てしまう。**読む鍵を明示する。**

## 完了条件
- [ ] `staging-bootstrap.yml` に読み取り専用の phase がある
- [ ] `SELECT` 以外を実行しない（走査で固定）
- [ ] production でも同じ phase が使える（環境は入力から取る）
- [ ] runbook（`platform-bootstrap.md` §10）から参照されている

## やらないこと
- 書き込み・削除の経路を足すこと
- `detail` を丸ごと出すこと
- 監査ログを画面（`/plat/*`）に出すこと（それは PF-13 の担当）
