## この task が起票された理由

競合（YOHAKU清掃管理）は「清掃報告 → 請求書発行 ＋ 給与計算」を一体化しており、
清掃会社の経理負担軽減が購買理由になっている。ProofKeeping は請求側
（タスク実績 → 請求明細）だけを持ち、**同じ実績データからスタッフへの支払を
出す経路が無い**。実績の二重入力（本システム＋給与 Excel）が残る。

PK-SPEC-P8 §1.2 は「給与計算は範囲外」と定めるが、オーナー指示（2026-08-19）で
**支払集計（支給総額の基礎まで）** を P8 から切り出して先行実装する。
控除（社会保険・源泉徴収・年末調整）は引き続き範囲外。CLAUDE.md §9 に例外を記録済み。

## やること

### 1. スキーマ（新テーブル 4 つ・additive migration）
- `staffPayProfile`: membershipId(unique) / employmentType(FULL_TIME|PART_TIME|CONTRACTOR)
  / invoiceRegistrationNo / isActive。※P8-01 `staffProfile` の先行サブセット。
- `payRule`: `pricingRule` のミラー。membershipId? / propertyId? / taskType? /
  unitType(PER_TASK|HOURLY) / unitPrice(整数円) / validFrom/To / priority。
- `payoutPeriod`: membershipId / periodFrom/To / status(OPEN→REVIEWING→CONFIRMED)。
- `payoutLine`: lineType(TASK|ADJUSTMENT|REIMBURSEMENT)。TASK 行は集計元 taskIds を保持
  （請求 §6.3 と同じ証跡接続）。

### 2. 計算エンジン（`packages/billing/src/payout.ts`・純粋関数）
- PER_TASK: 完了タスク件数 × 単価。HOURLY: `taskTimeLog` 由来の実働分 × 時給
  （**`cleaningTask.actualMinutes` を根拠にしない** — schema の注記どおり
  `accumulateActualMinutes()` を使う）。
- 単価解決は billing.md §8 の 5 段階をミラー。**該当なしは unitPrice=0 で計上し警告**。
- 整数円のみ。`ctx.now` 注入。正例・負例 5 件以上ずつ。

### 3. API（`/api/v1/payouts`）と画面
- 新アクション `payout.read` / `payout.write` = **OWNER / ORG_ADMIN のみ**
  （P8 §1.3「単価を PROPERTY_MANAGER に見せない」。CLIENT_VIEWER / AUDITOR も DENY）。
- 一覧・集計実行（再計算方式・冪等）・調整行の追加（理由必須）・確定。
- 画面: `/app/org/payouts`（月×スタッフ）と `/app/settings/pay-rules`（単価設定）。
  画面に「評価には使用しません」を明記（security.md §5）。比較・ランキングを出さない。
- 確定時 `recordAudit`（新アクション `payout.confirmed`）。

### 4. 帳票
- 支払明細書 PDF（`packages/pdf`）。採番は `DocumentSequencer` 経由
  `PAY-{西暦}-{連番4桁}`。発行済みの削除・更新 API を作らない。
- CONTRACTOR は仕入明細書方式（登録番号欄・税区分）。雇用スタッフは
  給与ソフト向け CSV エクスポート。
