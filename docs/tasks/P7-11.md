### 何もしなかったこと（意図的）

**新しい仕組みを足していない。** P7 固有の絶対ルールは
「新規機能を追加しない」。§5.2 が求めるのは「壊れたときに優先度 1 が
残ること」で、それを担う仕組み（送信キュー・my-day のキャッシュ）は
P1-12 / P1-21 で置いてある。**この task は動くことを確かめ、
後から静かに壊れないように性質を固定するもの**（DECISIONS #161）。

**優先度を見て機能を止めるコードを書いていない。** §5.2 は
「壊れたときにどこから諦めるか」を定めた表であって、
平常時に何かを止める指示ではない。優先度で分岐する実行時のコードを
足すと、**平常時の経路が 1 本増えて優先度 1 が壊れやすくなる。**

### 確かめたこと

完了条件 1（優先度 1 が障害時も維持される）:
- 開始・完了・再開が**画面から直接 `fetch` されず、必ず送信キューを通る**
  （`m/today.tsx` / `m/task.tsx` をソースごと走査）
- 押した瞬間に画面が動く（楽観的更新）。送信の成否を待たない
- 参照は取得に失敗したら `readCachedMyDay()` へ落ちる。例外を投げない
- IndexedDB が使えなくてもメモリへ退避して送信が続く
- 復帰の合図が `online` / `visibilitychange` の 2 つ以上ある
  （Background Sync API に依存していない）
- 優先度 1 のルートを一律で塞ぐ middleware が無い

完了条件 2（D1 書き込み失敗をオフラインキューが吸収する）:
- 500 / 502 / 503 / 504 が `RETRY`
- **5 回を超えても `DONE` にならない。** キューから消すのは `DONE` の
  分岐だけで、`GIVE_UP` は赤バッジを立てて書き戻す
- 409 は成功として畳む（D1 が書けていた場合の二重送信）
- 通信そのものの失敗も同じ扱い

### 積み残し

**`schemaVersion` 不一致で書き込み系 API を 503 にする middleware は
まだ無い**（§5.3 MUST / `packages/db/src/health.ts` の注記）。
P0-20 が範囲外とし、そのままになっている。**§5.2 とは両立する**
（503 はキューが吸収する）ので、この task では手を入れていない。
実装するときは 4xx で塞がないこと。4xx は `verdictOf()` が
`GIVE_UP` にするので、**吸収されずに赤バッジへ落ちる。**
