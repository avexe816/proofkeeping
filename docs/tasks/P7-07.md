### 判断したこと（止まらずに進めた）

- **手順 2・3 だけを自動化した**（DECISIONS #162）。手順 4（`SHARD_MAP` の
  書き込み）と手順 6（旧シャードの取り外し）は CLI が値を出力するだけ。
  **手順 1（読み取り専用への切り替え）が自動化できない**ため、
  照合が通った時点のデータが最新である保証が無い。既定は `--plan`。
- **移送する表は移送元の `sqlite_master` から取る。** schema の定義から
  作ると「schema に載っていないが D1 には在る表」が置き去りになる。
  移送は取りこぼしが即データ消失になるので、**知らない表は移す側**に倒した。
  移してはならない表（`schema_version` / `org_directory`）だけを名指しで除く。
- **チェックサムを行の並びに依存させない。** 移送先の `SELECT` が
  移送元と同じ順で返す保証は無く、順序の違いだけで不一致になると
  照合が使い物にならない。列の並びにも依存させない。

### 確かめたこと

- 行数が合っていても**チェックサムが違えば止める**（型の丸め・列の欠けは
  行数に出ない）
- 移送先に**作られなかった表**・**余分な表**を見逃さない
- `mayProceedAfterVerify()` が偽なら手順 4 へ進ませない
- `assertShardMapValue()` が範囲外を弾く（DECISIONS #007 の書き込み側の責任）
- **明示マッピングがハッシュより優先される**のは `router.spec.ts` が
  P0-03 から押さえている（「明示マッピングがハッシュより優先される（0 → 1）」
  ほか 6 件）。`shardMapKey()` が読み取り側と同じ綴りであることを追加した

### 人間が実施すること

**検証環境で実際に移送を 1 回通す。** 実 D1 が 2 本（移送元・移送先）要る。

```bash
pnpm shards:move --env staging --org <organizationId> --to 09          # 計画だけ
pnpm shards:move --env staging --org <organizationId> --to 09 --copy   # コピー＋照合
```

照合が通ったら、CLI が出力する値を `SHARD_MAP` へ書く（**TTL を付けない**）。
旧シャードの取り外しはその後。
