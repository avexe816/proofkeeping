## 作業ログ

### 2026-08-13 実装完了

**engine（純粋関数）**
- `packages/engine/src/evidence.ts`
  - `canonicalJson(value)` … §6.2 の正規化。キーはコードユニット順、
    配列の順序は保つ、`undefined` は落とし `null` は残す、
    **数値は整数のみ**（小数・NaN・Infinity は `CanonicalJsonError`）。
    `JSON.stringify` の replacer で済ませていない（キーの順序を制御できず、
    挿入順＝コードの行順に依存してしまう）。
  - `isoUtc(epochMs)` / `chainHashInput(previousHash, payloadSha256)` /
    `GENESIS_HASH`。
  - payload の組立 3 種（清掃完了・検査・再清掃完了）。
  - `verifyEvidenceChain(inputs)` … `payloadMatches` / `chainMatches` /
    `linkMatches` を**別々に**返す。`linkMatches` を分けてあるのは
    **途中の 1 件の削除を検出するため**（残った行はそれぞれ自己整合になる）。
  - 37 テスト。ハッシュ前の文字列を期待値に置いてある（64 桁の 16 進だと
    並びの誤りとハッシュの誤りが区別できない）。

**apps/web/src/lib/evidence/**
- `hash.ts` … `sha256Hex()` / `sha256HexOfText()`。WebCrypto は engine に
  持ち込まない（同期の純粋関数だけにしておく）。13 テストで NIST の
  テストベクタを固定。
- `record.ts` … 正規化 → payload ハッシュ → 直前の連鎖 → chainHash → INSERT。
  **失敗を業務操作へ伝播させない**（戻り値で返す）。payload は**関数**で
  受ける（DECISIONS #074）。
- `payload.ts` … 材料を DB から引く。**項目の並びは清掃時のチェックリスト順**に
  揃える（検査者が触った順だと同じ結果から違うハッシュが出る）。
- `verify.ts` … 保存された文字列をそのまま読み直してハッシュする。
  正規化を通し直さない（実装を変えた日に全件不一致になり改ざんと区別できない）。

**DB**
- `repositories/evidence.ts`。**INSERT と SELECT だけ。**
  `repositories.spec.ts` がソースを走査して `update` / `delete` を禁じている。
- `task_photo.sha256` を追加（migration 0008）。P1-11 の時点で列が無く、
  §6.3 の「DB の sha256 と R2 object metadata の双方へ保存」が
  **清掃写真では満たされていなかった**（検査写真は P2-01 から持っている）。
  nullable にしてあり、既存の行は `null` のまま。**後から計算して埋めない。**

**書く経路（3 か所）**
- 清掃完了 → `CLEANING_COMPLETION`（`lib/task/transition.ts`）。
  **`reworkCount === 0` のときだけ**（DECISIONS #073）。
- 検査確定 → `INSPECTION_PASS` / `INSPECTION_FAIL`（`lib/inspection/complete.ts`）。
  差戻しサイクルを作った**あと**に書く（payload に `reworkRequired` が入る）。
- 再清掃完了 → `REWORK_COMPLETION`（`lib/rework/advance.ts`）。

**API**
- `GET /api/v1/tasks/:taskId/evidence/verify`（§6.3 / §12.2 の「整合性を確認」）。
  権限は `task.read`。W-07（P2-09）がこれを呼ぶ。
