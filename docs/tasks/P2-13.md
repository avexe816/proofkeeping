## 作業ログ

### 2026-08-13

`/m/report?taskId=...`。入口は M-03（タスク詳細）の「忘れ物・不具合を報告」。

**3 タップの数え方**

```
1 タップ目  [ 忘れ物 ] / [ 設備・清掃の不具合 ]   §11.5 の 2 択
2 タップ目  区分（カテゴリ）のチップ
3 タップ目  [ 写真を撮る ]
```

**説明と場所の入力は写真より後ろに置いた。** 現場は「まず撮る」で、
文字を打つのは落ち着いてから（ui-writing.md §4）。区分と重要度には
既定値があり、**そのままでも送れる。** 撮影が 4 タップ目に落ちる
並べ方にしないこと。

**写真の受け口を作った（OPEN_QUESTIONS #051 の回答）。**
`POST /api/v1/{lost-items,issues}/:id/photos`（`multipart/form-data`）。

**手順を `lib/photo/pipeline.ts` へ抜き出した。** サイズ・形式の検査 →
EXIF 除去 → SHA-256 → R2 は、P1-11（清掃）と P2-04（検査）に**同じ形で
2 回**書かれていた。P2-13 が 2 経路を足すと 4 回になる。
**順序を間違えた 1 か所が静かに壊れる**（EXIF を落とす前にハッシュを
取ると、R2 の実体と DB の値が食い違い §6.3 の照合が常に失敗する）。
経路ごとに違うのは「親を引く・権限・INSERT 先」の 3 つだけで、
それは呼び出し側に残した。

`CRITICAL` は画面のチェックとサーバーの `confirmed` の 2 段（§8.2 MUST）。
ui-writing.md §3 は確認ダイアログを禁じるが、客室を止める操作は例外。

--- 申し送り ---
申し送り 1: **オフラインキューに載せていない。** 忘れ物は管理番号の採番を
            伴い、不具合は客室を止めうる。「送れたか」がその場で分からないと
            困る（M-09 / M-12 と同じ判断 / DECISIONS #068）。
申し送り 2: **写真は 1 枚だけ撮らせる。** §7.5 は「全体が分かる写真 1 枚」、
            §8.1 は「1 枚以上」。API は枚数を制限していないので、
            複数枚が要る画面が現れたら画面側だけを変えればよい。
申し送り 3: **写真が無くても報告は通る。** §7.5 / §8.1 の「必須」を
            サーバー側で強制していない（`PHOTO_REQUIRED` は用意済み）。
            報告を立ててからでないと写真の置き場が決まらないため。
            W-09 / W-10 が「写真なし」を出すのが現実的（OPEN_QUESTIONS #053）。
