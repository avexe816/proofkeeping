### 2026-08-12 完了

**書き込みだけを作った。読み取り・検索・エクスポートは作っていない。**

追加したもの:

| ファイル | 内容 |
|---|---|
| `packages/db/src/mask.ts` | `maskSensitive()` / `serializeAuditPayload()` |
| `packages/db/src/repositories/audit.ts` | `AUDIT_ACTIONS` レジストリと `recordAudit()` |

- **`action` は閉じたレジストリ**（`AUDIT_ACTIONS`）にした。security.md §6 の
  箇条書き 1 行が 1〜数エントリに対応する。5 年残る永続データで表記を後から
  揃え直せないため、開いた `string` にしていない（`ENTITY_PREFIXES` と同じ方針）。
- **マスクは書き込み経路の内側**に置いた。`user` の行をそのまま渡してよい。
  呼び出し側の規約にすると、消し忘れが**削除できない表**（INV-30）に溜まる。
- `requiresReason` が真の 2 操作（`room.statusOverridden` /
  `observation.amended`）は `reason` が無いと落ちる。
- `recordAudit()` は `TenantContext` を取り、`actorRole` は `ctx.role`、
  `at` は `ctx.now` から入れる。引数で受け取らない（PK-SPEC-P0 §19.5）。
- INV-30 は spec で固定した。`auditLog` への `update` / `delete` が
  リポジトリのソースに現れないこと、`audit.ts` の公開関数が `recordAudit` 
  ただ 1 つであることを `audit.spec.ts` が走査して検査する。

P0-08 の申し送り B（ログイン失敗 5 回目の監査ログ）を消化した:

- `apps/web/src/lib/auth/login.ts` の `registerFailure()` に接続。
  `PASSWORD_FAILURE_AUDIT_AT = 5`。**ロックの閾値 10 回とは別の定数**。
- 5 回目でだけ `membership` を 1 回引く（`actorId` / `actorRole` が
  NOT NULL のため）。通常のログインにも各試行にも D1 の読み取りは増えない。
- 監査ログの書き込み失敗は握りつぶす。ここで 500 にすると
  「`AUTH_FAILED` 一本」の原則が崩れ、応答から失敗の理由が読める。
- IP を `LoginInput.ip` で受け取る（ハンドラが `clientIp()` で渡す）。
