## この task が起票された理由

だけで、**取引先には何も届かない**。仕様 §6.1 の「（ホテル側に通知）」に対応する
送信経路が無く、清掃会社は電話・メールで別途伝えている。
PK-SPEC-P5 §13 が挙げる「ホテルが ProofKeeping 未導入の場合のメールリンク簡易承認」
を実装し、#078 を決着させる。

## やること

### 1. 確認依頼メールの送信
- `request-review` 成功時に `QUEUE_NOTIFICATION` へ新 kind
  `REVIEW_REQUEST_DELIVERY` を投入。宛先は `counterparty.billingEmail` + `ccEmails`。
- `DELIVERY_DOC_TYPES` に `REVIEW_REQUEST` を追加し、送付ログは
  `recordDocumentDelivery(QUEUED)` → `SENT/FAILED` の既存フロー
  （`deliverInvoice()` と同型）。#078 の「docType を増やす」案を採用。
- 本文はプレーンテキスト。金額・個人名・差異の詳細を書かない。禁止語 grep 対象。
- `recordAudit`: 新アクション `billingPeriod.reviewRequested`。

### 2. 署名付きリンク
- HMAC-SHA256（鍵は `SESSION_SECRET` 流用 — signedUrl.ts の既存判断踏襲）。
  署名対象 `${billingPeriodId}\n${issuedAtMs}\n${exp}`。**有効期限 30 日**
  （支払サイト既定 30 日に合わせる。DECISIONS に記録）。
- `lib/storage/signedUrl.ts` の `hmac()` / `timingSafeEqual()` を共通部品に切り出す。

### 3. 公開画面 `/r/billing/:billingPeriodId`
- `routes.ts` のトップレベル（layout 外・`/login` と同格）。
- loader: 署名・期限検証（失敗は 404）→ 明細を読み取り専用表示
  （`buildPeriodDraft()` 再利用）→ 証跡ドリルダウンは**載せない**（写真の署名 URL は
  セッション必須のため。閲覧はアカウント発行 = P5-16 に誘導）。
- action: 承認 / 差戻し（コメント必須）。`byCounterparty: true`、
  `actorId` は `systemActorId()`、新列 `billingPeriodReview.externalActorEmail` に
  宛先メールを記録（additive migration）。
- 状態が REVIEWING 以外なら操作を出さない（AGREED 済みは「承認済み」表示）。
- レート制限: `RATE_LIMITS` に `reviewLink`（30 req/分/IP）を追加。
  429 + `Retry-After`（webhooks.ts のパターン）。

## 完了条件
- [ ] 確認依頼で取引先にメールが届き、送付ログが `documentDelivery` に残る
- [ ] リンクから明細を閲覧し、承認・差戻しできる（履歴に `byCounterparty: true`）
- [ ] 期限切れ・改竄リンクは 404
- [ ] REVIEWING 以外への承認は 409
- [ ] 確認依頼の再送が冪等（dedupe）で、リンクは再発行される
- [ ] `RESEND_API_KEY` 未設定の環境で送信をスキップして落ちない
- [ ] `pnpm check` 通過

- **リンクからの証跡（写真）閲覧。** 発注元が証跡まで見る場合はアカウント発行
  （P5-16）で対応する。
- **入金消込・支払通知。**（OPEN_QUESTIONS #076 は据え置き）
