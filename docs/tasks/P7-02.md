## 実装計画

1. **QR の符号化**（純粋・ブラウザで動く）
   - バイトモード・誤り訂正 M で足りる。載せるのはログイン URL 1 本で、
     **版 1〜4 に収まる**（版 4・M・バイトモードで 62 文字）。
   - **誤った QR は「読めない」より悪い**（別の場所へ飛ぶ）。
   - **検証は往復で行う。** この環境には照合先になる QR の実装が無い
     （`python3 -c "import qrcode"` も `segno` も node の依存も無い。確認済み）。
     **既知のベクタを記憶から書き写さないこと。** 代わりに spec の中で
     **最小の復号**を書き、`encode() → decode()` が元の文字列に戻ることを
     確かめる。マスクの解除・RS の検算・埋め草の除去まで通るので、
     構造の誤りはここで落ちる。
   - 実機のスマートフォンで 1 回読ませるところまでは人が行う（自動化しない）。
   - ブラウザ側で描く。SSR は `ssr: true` でハイドレーションが効くので、
     `useEffect` で `<svg>` を組み立てればよい（**確認済み**）。
2. **印刷用の画面**
   - `cleaner-guide.html`（P7-15）と同じ作り。`@page` は A4、余白 0。
   - **PIN は画面を生成するリクエストの中だけ。** loader へ渡さない
     （loader は GET で、URL にも履歴にも残る）。
   - スタッフを登録した直後の `action` の戻り値としてだけ現れる。
3. **走査で押さえる**
   - `pk-pdf-generation` へ案内カードを投げていないこと。
   - PIN を `recordAudit` / `console` / R2 へ渡していないこと。

## 前提

- スタッフの登録は `POST /api/v1/users`（P7-01）。**PIN はその応答に
  1 回だけ現れる**（DECISIONS #177）。**保存し直さないこと。**
- 登録の**画面**はまだ無い（OPEN_QUESTIONS #103）。この task で
  画面を作るなら、そこが案内カードの出口になる。
