`schema/report.ts` に 3 表（`issueReport` / `issuePhoto` / `issueHistory`）。

**`room.saleStatus` の列を足した。** §8.2 MUST が `Room.saleStatus = OUT_OF_ORDER` を
要求するが、`room` にその列が無かった（清掃ステータスしか無い）。
`ROOM_SALE_STATUSES = ["AVAILABLE", "OUT_OF_ORDER"]`、既定 `AVAILABLE`。
**追加のみで既存列を触っていない**（architecture.md §6 の後方互換）。

**完了条件の満たし方**

| 条件 | どこで守っているか |
|---|---|
| CRITICAL で客室が OUT_OF_ORDER + BLOCKED | `reportIssue()` が `setRoomSaleStatus()` と `setHousekeepingStatus()` を**両方**呼ぶ。engine の `roomEffectOf()` が `AUTO_BLOCK` を返すのは `CRITICAL` だけ（`HIGH` は `SUGGEST_BLOCK`＝自動では止めない） |
| 解決しても客室が自動復旧しない | `changeIssueStatus()` / `advanceIssueReport()` が `room` に一切触らない。engine にも「戻してよい」を返す関数が無い。復旧は W-03 の手動上書き（`room.statusOverride` / 理由必須・監査ログ） |

§8.2 MUST の「確認画面を出し、確定後に」は**サーバー側でも要求する**
（`confirmed: true` が無ければ 409 `CONFIRMATION_REQUIRED`）。画面だけの確認は
API を直接叩けば迂回できる。

客室を止めたときは `room.statusOverridden` を監査ログへ残す（理由＝不具合の題名）。
自動であっても客室が止まる事実は手動上書きと同じ重さを持つ（security.md §6）。

engine `issueRules.ts`（24 テスト）が §8.2 の表と §3.6 の状態機械。
`RESOLVED` に解決内容を必須にした判断は DECISIONS #081。
