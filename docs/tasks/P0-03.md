## 完了条件
- [x] `SHARD_COUNT=1` と `16` の両方で動く
- [x] 1600 組織を生成し、16 シャードへの分散が均等（最大偏差 ±30% 以内）
- [x] 100 組織で 16 シャードすべてに 1 件以上落ちる（分岐の網羅）
- [x] KV の明示マッピングがハッシュより優先される
- [x] binding 欠落時に明確なエラーメッセージが出る

> 完了条件の 2 番目は当初「100 組織を生成し、最大偏差 ±30% 以内」だった。
> 100 組織・16 シャードでは 1 シャードあたり平均 6.25 件・標準偏差 ≈2.4 に対し
> 許容幅が ±1.9 件しかなく、一様ハッシュでも統計的に達成できない（実測 -84%〜+108%）。
> 判定件数を 1600 に増やし、100 組織側は「全シャードに 1 件以上」に分離した。
> 経緯は `docs/DECISIONS.md` #008。

**判断したこと**
1. **不正値はフォールバックせず例外にする。** `SHARD_MAP` の値が数値でない・
   負数・`SHARD_COUNT` 以上の場合、および `SHARD_COUNT` 自体が不正な場合は
   `SHARD_MAP_INVALID` / `SHARD_COUNT_INVALID` を投げる。ハッシュへ静かに
   落ちると移送済み組織のデータが複数シャードへ分裂し、越境テストにも
   引っかからないため（DECISIONS #007）。
2. **`SHARD_MAP` への書き込みは本 task で作らない。** task の やること が
   読み取り側の 4 関数のみのため。所有 task が無いことは OPEN_QUESTIONS #007 に記載。
3. **`fnv1a32` は自前実装。** 仕様 §19.3 の 7 行をそのまま持つ。外部パッケージに
   委ねると更新でバケット割当が変わり、移送手続きを踏まないままデータが
   別シャードへ向かう。標準テストベクタを spec で固定した。
4. **`getTenantDb()` は非同期。** KV を読むため。仕様 §19.3 のコード例は同期だが、
   完了条件が KV 優先を要求するため非同期を採った（OPEN_QUESTIONS #008）。
