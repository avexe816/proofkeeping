**置き場所が §9 と違う。** §9 は `packages/engine/src/{types,confidence,
suppression}.ts` と書くが、そこには P1〜P3 のモジュールが 25 個ほど並んで
おり、`types.ts` を置いても何の型か読めない（`baseline.ts` は既に P3 の
ものが居る）。`reconciliation/` にまとめ、公開の口（`src/index.ts` からの
re-export）は §9 のとおりにした。

**純粋であることを spec で固定した**（`reconciliation/purity.spec.ts`）。
`Date.now()` / 引数なし `new Date()` / `Math.random()` / `fetch(` /
`process.env` / `crypto` と、`@pk/db` などへの import をソース走査で落とす。
**実際に 4 つを注入して落ちることを確認した**（規約を書くだけにしない）。
ルールを足す task が `rules/` にファイルを置けば自動的に検査に入る。

**確信度の調整をルールの外に置いた。** §4.2 の調整は全ルールに等しく
掛かるので、各 `evaluate()` の中で掛けると 14 個のうち 1 つだけ掛け忘れた
形が生まれる。ルールは素の値を返し、`evaluate()` が最後にまとめて掛ける。

**抑制はルールを呼ぶ前に効く**（§4.3）。呼んでから捨てると「差異が出たが
抑えた」と「そもそも該当しなかった」が混ざり、`findingsSuppressed` の
件数が意味を失う。抑制した理由は 7 種のコードで返す（**仕様は理由の語彙を
定めていない**。§4.3 が内訳の可視化を求めるので置いた）。

**R010 / R014 の入力はまだ `RuleContext` に無い。** R010 は客室ステータスの
手動上書き履歴（`auditLog`）、R014 は稼働記録の変更履歴を要する。どちらも
既存の表から直接は引けない。**推測で欄を作らず、実装する task（P4-12）が
足すこと**を型のコメントに書いてある。なお R014 の入力は P4-02 が残す
`occupancy.imported` の差分（`isOccupied: true → false`）で作れる見込み。

**R001 と R002 の統合（§3.3 MUST）はここではない。** R002 を実装する
P4-11 が行う。片方しか無い段階で統合の枝を書くと検証できない分岐が残る。
