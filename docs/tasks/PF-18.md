# PF-18 `staging-bootstrap.yml` の `db-status` が表の数を 0 と出す

**系列**: PF（起票 2026-08-21 / PF-16 の着手時に観測）
**依存**: なし **見積**: 0.5日 **ステータス**: 未着手
**未解決**: `docs/OPEN_QUESTIONS.md` #116

## 背景

`staging-bootstrap.yml` の `phase=db-status`（読み取り専用）の出力で、
**shard-00 / shard-01 とも「表の数」が 0** と表示される。

**表は実在する。** 同じ時点で次が確かめられている（2026-08-21）。

- `/api/health` が ok
- `schemaVersionConsistent = true`
- `schema_version` が両 shard で 0000〜0034 の 35 本一致

つまり**数え方の側の不具合**で、DB の状態ではない。

**PF-16 のスコープに入れなかった**（人間の指示 2026-08-21）。
開通の経路とは無関係で、混ぜると PR が読みにくくなる。

## やること

1. `db-status` phase が表を数えている SQL と、その結果の取り出し
   （`wrangler d1 execute` の出力 → `jq` の経路）のどちらが噛み合って
   いないかを特定する
2. 直す。**読み取り専用の phase であることを崩さない**
3. 数え方が壊れたときに 0 ではなく**失敗として出る**ようにする
   （「0 表」と「数えられなかった」を区別する）

## やらないこと

- `db-status` に書き込みの手を足すこと
- 表の数以外の項目を増やすこと（**プロトタイプが上限**の原則）
- `reset-db` / `mark-applied` の条件を触ること

## 完了条件

- [ ] `db-status` が実際の表の数を出す（両 shard）
- [ ] 数えられなかったときに 0 と表示しない
- [ ] 他の phase の挙動が変わっていない

## なぜ急がないか

読み取り専用の phase で、**誤った数字が出る以外の実害は無い。**
ただし「表が無い」と読み違えると、要らない `reset-db` や `mark-applied` を
押しかねない（どちらも合言葉が別なので即座には起きない）。

表の有無は、直るまでは次で確かめる。

```bash
# /api/health の schemaVersionConsistent
pnpm db:migrate --env staging --check
```
