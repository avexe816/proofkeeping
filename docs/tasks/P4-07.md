## 作業ログ

### 2026-08-14
- API `GET /api/v1/findings/:id` / `PATCH /api/v1/findings/:id/status` と
  画面 `/app/audit/findings/:findingId`（`routes/app/findingDetail.tsx`）。
- **3 系統は差異の `evidence` から作っていない。** `evidence` は
  ルールが判定に使った部分の写しで、ルールごとに形が違う。§6.2 は
  「そのとき何が記録されていたか」を並べる画面なので、
  `occupancySnapshot` / `roomObservation` / `physicalSignal` を
  引き直して組み立てる（`lib/reconciliation/findings.ts`）。
- 応答の `sources` は**常に 3 つの鍵を持つ。** 欠けている系統は `null` で、
  画面がその枠に「データなし」を出す。枠ごと消さない（§6.2 MUST）。
  観察は「記録が無い」と「今回は記録しないを選んだ」を区別するため
  `observationSkipped` を別に返す（PK-SPEC-P3 §1.3）。
- 解決コードは §6.3 の 2 系統。`RESOLVED` 側 7 / `FALSE_POSITIVE` 側 4 で、
  **状態と組み合わせが合わないものは 400。** `OTHER` は理由必須。
  検証は Zod（`findingStatusRequestSchema`）に閉じてあり、API と画面の
  action が同じスキーマを通る。
- `FALSE_POSITIVE` は `detectionFeedback` に 1 行足す（§1.4 / §2.6）。
  `RESOLVED` + `CONFIRMED_DISCREPANCY` は `TRUE_POSITIVE` として残す。
  他の解決コードは「原因が別にあった」で、ルールが当たっていたかを
  言っていないので記録しない。
- 状態変更は `OWNER` / `ORG_ADMIN` だけ（§6.4）。新しい権限
  `finding.write` を足した。**施設責任者は読めるが閉じられない。**
- 監査ログは既存の `finding.statusChanged`（security.md §6）。
