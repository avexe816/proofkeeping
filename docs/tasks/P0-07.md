## 完了条件
- [x] 全リポジトリ関数が `TenantContext` を必須引数に取る
  - 例外は認証ブートストラップの 2 関数（`findMembershipByUserId` /
    `listAssignedPropertyIds`）。これらは `TenantContext` を**作るための**関数なので
    `ShardContext` を取る（DECISIONS #016）。2 つに固定してテストで縛ってある。
- [x] `organizationId` が自動付与される
  - `withTenantScope()` が必ず `eq(table.organizationId, ctx.organizationId)` を載せる。
    全リポジトリ関数の発行 SQL を `repositories.spec.ts` が表駆動で検証する。
- [x] 施設スコープロールで担当外が取れない
  - `scopeToProperties()` が `IN (...)` を張る。**担当施設が空なら 0 件**（全件ではない）。

**設計の要点**
- `TenantContext` に `role` / `allowedPropertyIds` / `now` を追加し、
  シャード解決だけに要る最小限を `ShardContext` として切り出した（DECISIONS #016）。
  業務リポジトリに `ShardContext` を渡すとコンパイルが通らないことを実測で確認。
- `scopeToProperties()` は `undefined` を返さない全域関数。`and()` が `undefined` を
  黙って捨てる性質で施設スコープが消える経路を無くした（DECISIONS #017）。
- 施設列は `withTenantScope()` の第 3 引数で**必ず明示**する。持たない表は
  `NO_PROPERTY_SCOPE` と書く。省略を許すと書き忘れと区別がつかない。

**テスト（47 件追加 / 全体 270 件）**
- `repositories.spec.ts` が**モジュールの export を走査**し、`INVOCATIONS` に
  登録の無い関数があれば落ちる。→ **関数を追加したら自動的に検証対象に入る。**
  登録すれば「organization_id 条件つきの SQL を発行する」「越境 ID で
  DB へ触れずに `NotFoundError`」がそのまま掛かる。
  未登録が検出されることは、仮の関数を足して実測済み。
- 実 D1 は使わず SQL を記録する代役に注入（`migrate.spec.ts` と同じ方式）。
  P0-02 が未完で実在する D1 が 1 本しかないため。

**申し送り**
- `TenantScopedTable` は `organizationId` を持たない表（`schema_version`）を
  型で弾くが、**`org_directory` は同列を持つため型では弾けない。**
  リポジトリが全局テーブルに触れていないことはソース走査のテストで担保している。
- `listUsers` に施設の絞り込みは掛けていない（OPEN_QUESTIONS #016）。
  到達可否は P0-10 の `assertPermission()` の責務。
- 越境テスト（`tests/tenant-isolation/`）は P0-13 の所有。ここでは作っていない。
