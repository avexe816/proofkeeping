## 作業ログ

### 2026-08-11 実装

`apps/web/wrangler.toml` を新規作成し、PK-SPEC-P0 §9.2 の 4 環境を宣言した。

| 環境 | Worker 名 | D1 | `SHARD_COUNT` |
|---|---|---|---|
| local（top-level） | `pk-local` | 1（SHARD_00） | `"1"` |
| `[env.preview]` | `pk-preview` | 1（SHARD_00） | `"1"` |
| `[env.staging]` | `pk-staging` | 2（SHARD_00–01） | `"2"` |
| `[env.production]` | `pk-prod` | 16（SHARD_00–15） | `"16"` |

wrangler の `[env.*]` は top-level の binding を継承しないため、D1 / R2 / KV / Queue /
vars は環境ごとに全宣言している。実在しない D1 を staging / preview に宣言すると
`wrangler deploy` が落ちるので、各環境には実際に持つ本数だけを置いた。
task の「16 個の D1 binding を静的宣言」は `[env.production]` で満たしている。

binding の型は `packages/db/src/env.ts` の `Env` に定義した。
`packages/*` から `apps/*` は import できず、architecture.md §1 と §19.3 が
`packages/db/src/router.ts` に `getTenantDb(env: Env, ctx)` を置くと定めているため。

#### 宣言していないもの（意図的）

| 対象 | 理由 | 担当 task |

| `[[queues.consumers]]` | `queue()` ハンドラ未実装で宣言すると wrangler が起動しない | P2-10 / P3-09 / P4-14 / P5-06 / P6-04 / P7-09 |

#### ツールチェーン側の変更

- `package.json` に `dev`（= `pnpm --filter @pk/web dev` → `wrangler dev`）を追加。
  `tests/toolchain/workspace.spec.ts` の `DEFERRED_ROOT_SCRIPTS` から
  `EXPECTED_ROOT_SCRIPTS` へ移した。
- `typecheck` を 3 パスに分割した。`@types/node` と `@cloudflare/workers-types` は
  グローバル（`fetch` / `Response` など）が衝突するため同一プログラムに混ぜられない。
  ルート `tsconfig.json` で `apps/**` と `packages/db/**` を `exclude` し、
  それぞれ自前の tsconfig（`worker.json` を extends）で検査する。
- `pnpm-workspace.yaml` の `onlyBuiltDependencies` に `workerd` と `sharp` を追加。
  **これが無いと pnpm がビルドスクリプトを無視し、`wrangler dev` が起動しない。**
- `wrangler` は 4.x を入れた（3.x は `legacy` タグ）。
  wrangler 4 の peer に合わせ `@cloudflare/workers-types` を 5.x に上げた。

#### KV は 5 本（task の記述に `SHARD_MAP` を追加）

task の「やること」は KV を 4 本（SESSION / RATELIMIT / CONFIG / CREDENTIALS）と
書いているが、レビューでの指摘を受けて **`SHARD_MAP` を 5 本目として追加した。**

`shard:{organizationId}` を `CONFIG` に相乗りさせると、`CONFIG` の一括削除や
TTL 失効でキーが消えたとき `resolveShard()` がエラーにならず `fnv1a32` の
フォールバックに静かに落ちる。移送済みの組織では以後の読み書きが移送前の
シャードへ向かい、**同一テナントのデータが無警告で複数シャードに分裂する。**
越境テストにも引っかからない（テナント分離自体は破れていないため）。

失われてはならないデータと、失われてよいキャッシュを同じストアに置かない。
`SHARD_MAP` への TTL 付き書き込みは `.claude/rules/architecture.md` §1 で禁止した。
経緯は `docs/DECISIONS.md` #006、`docs/OPEN_QUESTIONS.md` #006（解決済）。

### リソース作成コマンド（手元で実行する）

実在するのは D1 の `proofkeeping-shard-00` のみ。
未作成の箇所は `TODO-P0-02-未作成-*` のプレースホルダにしてある。

```bash
grep "TODO-P0-02" apps/web/wrangler.toml
```

で未設定行を全件拾える。推測した UUID は 1 つも書いていない。

**local の分は作らなくてよい。** `wrangler dev` は miniflare が D1 / R2 / KV / Queue を
ローカルで模擬するため、`pk-photos-local` などのリソースは実在しなくても起動する。
top-level の KV `id` が `TODO-P0-02-未作成-*` のままでよいのはこのため。

```bash
cd apps/web

# --- D1: production の残り 15 シャード ---
for i in $(seq -w 1 15); do wrangler d1 create proofkeeping-shard-$i; done

# --- D1: staging（2 本）と preview（1 本）---
wrangler d1 create proofkeeping-shard-00-staging
wrangler d1 create proofkeeping-shard-01-staging
wrangler d1 create proofkeeping-shard-00-preview

# --- R2: 4 バケット × 3 環境 ---
for e in "" -staging -preview; do
  for b in photos documents evidence archive; do
    wrangler r2 bucket create pk-$b$e
  done
done

# --- KV: 4 namespace × 3 環境 ---
# 出力される id を、対応する環境の kv_namespaces の id に貼る。
for e in "" -staging -preview; do
  for n in session ratelimit config credentials shard-map; do
    wrangler kv namespace create "pk-$n$e"
  done
done

# --- Queues: 7 種 × 3 環境 ---
for q in pdf-generation evidence-export reconciliation rollup-update \
         baseline-learning notification archive-restore; do
  for e in "" -staging -preview; do
    wrangler queues create pk-$q$e
  done
done

# --- Secrets: 4 本 × 3 環境（local は apps/web/.dev.vars）---
for env in production staging preview; do
  for s in SESSION_SECRET RESEND_API_KEY CREDENTIAL_ENCRYPTION_KEY SENTRY_DSN; do
    wrangler secret put $s --env $env
  done
done
```

#### 出力の差し替え先

| コマンド | 出力 | 差し替える行 |
|---|---|---|
| `wrangler d1 create proofkeeping-shard-NN` | `database_id` の uuid | `[env.production]` の `SHARD_NN` の `database_id` |
| `wrangler d1 create proofkeeping-shard-0N-staging` | 同上 | `[env.staging]` の `SHARD_0N` の `database_id` |
| `wrangler d1 create proofkeeping-shard-00-preview` | 同上 | `[env.preview]` の `SHARD_00` の `database_id` |
| `wrangler kv namespace create pk-{name}{env}` | `id` の 32 桁 hex | 対応する環境の `kv_namespaces` の `id` |
| `wrangler r2 bucket create ...` | （id なし） | 差し替え不要。`bucket_name` は宣言済み |
| `wrangler queues create ...` | （id なし） | 差し替え不要。`queue` は宣言済み |

R2 と Queue は名前だけで参照するため、作成すればそのまま繋がる。
差し替えが要るのは **D1 の `database_id` と KV の `id` だけ**（local を除く）。
差し替え後に `pnpm test` を流すと、構成テストが宣言漏れを拾う。

#### ローカル起動の確認

```bash
cp apps/web/.dev.vars.example apps/web/.dev.vars
pnpm dev
```

`SHARD_COUNT=1` で起動し、ログに SHARD_00 / R2 4 本 / KV 5 本 / Queue 7 本の
binding が並べば成功。`http://localhost:8787` は 404 を返す
（P0-02 はルートを 1 本も定義しないため、これが正常）。

ローカルは miniflare の SQLite を使い remote D1 へは接続しない。
`SHARD_00` に実 `database_id` を書いてあるのは `--remote` 実行時の整合のためで、
通常の `pnpm dev` が本番データに触れることはない。
