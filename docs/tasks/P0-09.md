## 読むべきルール
security.md §2

## やること
**orgShortId＋スタッフ番号＋PIN 4 桁**でログインできるようにする。

P0-08 でログイン識別子を 3 フィールド（orgShortId + スタッフ番号 + 認証情報）に
統一したため、当初の「施設コード」は使わない（DECISIONS #018）。
セッション・Cookie 署名・レート制限・アカウントロックは P0-08 の
`apps/web/src/lib/auth/` を再利用し、PIN の検証と `/auth/pin-login` を足すだけにする。

**PIN のハッシュ方式を決めてから着手すること（OPEN_QUESTIONS #017）。**
P0-08 でパスワードは PBKDF2-SHA256 へ移したが、security.md §2 の PIN 行は
bcrypt cost 10 のまま残してある。PIN のためだけに bcryptjs を持ち込むかどうかの判断が要る。

PIN にも使う。反復回数だけ 50,000 へ下げる（実測 9.6ms / パスワードは 210,000 回で
37.8ms）。根拠は DECISIONS #021。security.md §2 の PIN 行を改訂済み。

### 未達の 2 件

**① 5 回失敗で 15 分ロック** — 実装していない。PIN の総当たりを止めているのは
`/auth/pin-login` の 20 req/分/IP のみ。`failedLoginCount` 列を**パスワードと
共有している**ため、中途半端に数えると「PIN の失敗でパスワードがロックされる」が
起きる。実装するなら**列を分けるところから**設計すること。
`pinLogin.ts` に「`registerFailure()` 相当をここに書かないこと」と理由付きで
コメントを残してある。なお**既に掛かっているロック（`lockedUntil`）は尊重する。**
管理者が別経路で掛けたロックを PIN で迂回できる状態は作っていない。

**② 初回ログインで変更が強制される** — PIN 変更画面が P1 以降のため、
強制する先が無い。`/auth/pin-login` の応答に `pinMustChange` を載せるところまで
実装した。**現時点では true を無視しても業務が通ってしまう。**

### 次の task への申し送り

- `hashPin()` を直接呼ぶと `pinSchema`（連番・ゾロ目の拒否）を迂回できる。
  `setPassword.ts` に相当する `setUserPin()` を作っていないため、PIN を書き込む
  経路を追加するときは**必ず `pinSchema` を先に通すこと。**
- PIN の反復回数を引き上げるときは `PIN_PBKDF2_PARAMS` と `pinLogin.ts` の
  `DUMMY_PIN_HASH` を**同時に**直す。片方だけだと、存在しない利用者への応答だけが
  遅く（または速く）なり、timing でアカウントの存在が読める。
- P0-10 の middleware は `authMethod` で 12 時間 / 16 時間を判別できる。
  セッションに `role` は入っていない（DECISIONS #020）。
