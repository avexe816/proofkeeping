## この task が起票された理由

事業目的「ホテル運営側にもアカウントを発行し、清掃結果を確認・照合できるようにする」
に対して、現行の 7 ロールに**発注元（ホテル側）を正しく写像できるロールが無い**。

| 候補 | 何が壊れるか |
|---|---|
| `OWNER` を発行 | 組織全体の最強権限（組織設定・税務・照合実行の write）。発注元が受注者の設定を書き換えられる |
| `AUDITOR` を発行 | 組織全体が読める。「自施設のみ」（契約 §4）に絞れない |

これは OPEN_QUESTIONS **#011**（契約 §4 の `OWNER`/`VIEWER` と security.md §1 の
`OWNER` が別概念）の未決部分そのものであり、この task で決着させる。

## やること

### 1. ロール定義
- `packages/db/src/schema/user.ts` の `ROLES` に `CLIENT_VIEWER` を追加（8 語目）。
  表示名は「発注元」。DB は素の text 列のためスキーマ変更不要。
- `membership` に `counterpartyId`（nullable）を追加。CLIENT_VIEWER のみ設定。
  additive migration（`pnpm db:generate`）。

### 2. 権限
- `PERMISSION_MATRIX` に CLIENT_VIEWER の全セルを記入。**フォールバック禁止**。
  権限の正は契約 §4 の OWNER/VIEWER 列: 清掃記録・検査結果・差異・日報・月次
  レポートは **ASSIGNED（担当施設）で read**、write は原則すべて DENY、
  氏名 ×・個人別実績 ×・シフト ×・検査実施 ×・手順変更 ×・請求確定 ×。
- 新アクション `billing.review`（合意/差戻し専用・write）を追加。
  CLIENT_VIEWER は自 counterparty の請求期間のみ `byCounterparty: true` で実行可。
- `ORG_WIDE_ROLES` には**載せない**（`allowedPropertyIds` 絞りを既定で効かせる）。
- `STAFF_NAME_HIDDEN_ROLES` に追加（契約 §4「清掃員の氏名 ×」）。

### 3. counterparty スコープ（第 1 層防御の拡張）
- `TenantContext` に `counterpartyId`（nullable）を追加。`middleware/tenant.ts` が
  membership から組み立てる。
- billingPeriod / invoice / receipt 系リポジトリで
  `ctx.counterpartyId != null` のとき counterpartyId の一致を**強制注入**する
  （`organizationId` 強制注入と同じ向き）。

### 4. メンバー管理・認証
- `PASSWORD_LOGIN_ROLES` / `ADMIN_STAFF_ROLES` / `ADMIN_ROLE_OPTIONS` /
  `ASSIGNED_ROLES` に追加。members 画面で CLIENT_VIEWER 選択時は
  **取引先の選択と施設割当を必須**にする。
- `ROLE_LABEL`（members.tsx / UserMenu.tsx）と `ja.json` / `en.json` に表示名。

## やらないこと
- **別テナント（ホテル法人の独立組織）との相互参照。** `user` は組織スコープで
  シャード分散しており、組織間参照は全シャード走査禁止（architecture.md §3）に抵触する。
- **契約 §4 の「再清掃の依頼（依頼可）」。** 依頼→運営管理者経由の経路（契約 §4.2）は
  通知基盤の整理後に別 task で起票する。
- **閲覧者の招待（契約 §4「自施設」）。** user.write は DENY のまま。招待は
  ORG_ADMIN 以上が行う。
