# PF-14 システム設定（画面 12 / 設計と運用を分ける）

**系列**: PF（起票 2026-08-20） **依存**: PF-01 **見積**: 1.5日 **ステータス**: 未着手
**仕様**: `ui-prototypes/platform/pkplat-D-contract-audit-config.html` 12 / route `/plat/config`

## 背景
> **この画面は左右2カラムに分けます**
> 左の「設計（変更不可）」と右の「運用（変更可）」を並べ、日々の調整で製品の原則が動かないことを明確にします。この構成自体が判断です。

**この構成自体が仕様。** 1 カラムにまとめない。

## やること

### 左「🔒 設計（変更不可）」— 読み取り専用の 7 項目
押すと「**コード上の定数です**」と出るだけ。**設定として書けるようにしない。**

1. 単一シグナルのみの場合は確信度上限 50
2. 清掃員氏名をオーナーに開示しない
3. ランキング機能を実装しない
4. 差異の自動通報を実装しない
5. 顔検出を実装しない
6. 監査ログの削除 API を実装しない
7. 記録件数での課金をしない

> 以下は製品UIの設定項目ではありません。表示は判断の一覧であり、切替を押すと「コード上の定数です」と表示します。

### 右「⚙️ 運用（変更可）」— 数値 5 つ
| 項目 | 既定 | 単位 |
|---|---|---|
| 入力所要時間の基準 | 10 | 秒 |
| 既定値のまま比率の閾値 | 70 | % |
| 写真の保存期間 | 90 | 日 |
| 1 人あたり担当室数の上限 | 16 | 室 |
| メンテナンス時間帯 | 03:00〜04:00 | 日本時間 |

**PF-02 / PF-05 の判定はこの値を読む**（ベタ書きしない）。

### 表「📋 変更申請と承認のルール」
- 運用（変更可）= 運営管理者が申請 → **承認者 2 名** → 次の運用開始時刻に反映
- 設計（変更不可）= 申請は記録として受け付けるが、**承認者 3 名全員の合意が
  あっても承認しない。** PK-SPEC-UI 第1章の改訂手続が必要

### 表「📝 直近の申請履歴」（日付 / 申請内容 / 判断 / 理由）

## やらないこと
- 左カラムの 7 項目を DB の設定値にすること（**コード上の定数のまま**）
- 承認 1 名での反映
- 「設計」の申請を承認できる経路

## 完了条件
- [ ] 左の 7 項目に書き込みの口が無い（走査テスト）
- [ ] 左の申請が**どう承認しても通らない**（承認者を 3 名揃えても反映されない）
- [ ] 右の 5 項目が承認 2 名で反映される
- [ ] PF-02 / PF-05 が右の値を読んでいる（閾値のベタ書きが無い）
- [ ] 変更が `platform_audit_log` に残る
