# P8-11 在留資格の保存期間と削除

**Phase**: 8（起票 2026-08-22 / **オーナー指示** / DECISIONS #261）
**仕様**: `docs/PK-SPEC-P8.md` §1.4 / `.claude/rules/security.md` §4・§5
**依存**: P8-02（在留資格の記録）
**見積**: 1日
**優先度**: **production の開通、または実在する従業員データの投入前に完了必須**
**ステータス**: 完了（2026-08-22 / DECISIONS #266、同日 hotfix #268）

## 背景

**在留資格の情報に保存期間の定めが無い。** 写真は 6 か月・上位プランで
13 か月（security.md §4）、退避は 13 か月（PK-SPEC-P0 §19.7）と定めがあるのに、
`residency_record` には期間の定めも削除の仕組みも無い。

**現在は無期限保持で、削除の経路が 1 本も無い。** `residency` は
archive / retention のどのコードにも現れない（2026-08-22 時点で確認）。
退職者の在留資格が、退職後もそのまま残り続ける。

INV-08 v2（DECISIONS #261）で閲覧できる相手を `OWNER` へ広げたので、
**残り続ける情報を読める人も増えた。** 期間を決めるのはその見返りにあたる。

## 法令の状況（起票時点の整理。**実装前に最新を確かめること**）

- **労働者名簿・賃金台帳等の法定保存期間は、退職日起算で 5 年。**
  ただし**経過措置により当分の間は 3 年**（労働基準法 109 条・143 条）。
- **在留カードの写しそのものには、明確な年数の定めが無い。**
  実務は「在留期間中は保管し、退職後も一定期間は保管」という運用が多い。
- **退職時に在留カード番号の記録を削除する実務もある**（保持の必要が
  無くなった個人情報を残さない、という考え方）。
  なお **ProofKeeping は在留カード番号を保存していない**（`residency_record` に
  その列が無い）。ここで扱うのは種別・期限・更新申請日だけ。

## 保存・削除の方針（**オーナー判断で確定 / 2026-08-22**）

> **在留資格の記録は、従業員の退職日から 3 年の保存期間が満了した翌日以降に
> 物理削除する。**

確定した仕様。**実装はこの定めに従う。**
（境界は 2026-08-22 の hotfix で「満了時点」から「満了の翌日以降」へ改めた /
DECISIONS #268）

### 起算と判定

- **起算日は従業員の退職日。** 在留期限でも、記録を作った日でもない。
- **満了日当日は削除しない。翌日以降のバッチから対象にする。**
  民法 140 条（初日不算入）で数えると 3 年の満了は当日の終了時で、
  07:00 JST のバッチで当日に消すと期間が満了していない。
  例: 2023-08-20 退職 → 満了 2026-08-20 → **2026-08-21 の回から**対象。
- **応当する日が無いときは、その月の末日が満了日**（民法 143 条 2 項）。
  例: 2024-02-29 退職 → 満了 **2027-02-28** → 2027-03-01 の回から対象。
  翌月 1 日へ送らない。
- **暦として存在しない退職日は削除対象にしない**（`2023-02-30` / `2023-00-15`
  など）。形が `YYYY-MM-DD` でも暦に無い値は判定の材料にならない。
  `Date.UTC` は範囲外の月日を黙って繰り上げるので、**壊れた値がそれらしい
  日付に化ける。** 判定できない入力は消さない側へ倒す。
- **退職日が不明な場合は自動削除しない。** 判定の材料が無い記録を、
  経過日数の推測で消さない。人が退職日を入れてから対象になる。
- **在職中の記録は、在留期限が切れていても削除しない。** 期限切れは
  削除の理由にならない（配分停止の理由にはなる / `assignmentBlock.ts`）。

### 通知との関係

- **退職した時点で、期限通知の対象から即座に外す。** 保存期間とは別に、
  すぐ効かせる。退職者へ更新の通知が飛ぶ状態を作らない。
  （現在の `countResidencyAlerts()` は `workStatus = RESIGNED` を数えないので、
  **ここは既に満たしている。** 削除の実装で壊さないこと。）

### 削除の対象と方法

- **削除の対象は在留資格の記録**（`residency_record` の行）。
- **在留カード番号は対象外。** ProofKeeping は在留カード番号を保存して
  いない（`residency_record` にその列が無い）。**列を足さないこと。**
- **物理削除にする。** 訂正の履歴を残す `EvidenceSnapshot` や帳票と違い、
  在留資格は「持たないこと」に意味がある。
- **削除処理は冪等。** 複数回実行しても結果が変わらない（testing.md §4）。
- **DELETE と監査ログを同じ D1 `batch()` で原子的に実行する**（hotfix #268）。
  どちらかが失敗したらその塊を丸ごと巻き戻す。別々の `await` にすると、
  間で落ちたときに**行は消えたのに記録が残らない**。retry では対象が
  0 件になるので、実際の削除件数を復元できない。

### 監査ログ

- 削除の実行時に **`residency.deleted`** を監査ログへ記録する
  （`AUDIT_ACTIONS` へ 1 行足す）。
- **監査ログに氏名・在留資格の種別・期限・更新申請日・退職日・スタッフ ID・
  対象 ID の一覧・その hash を残さない。** 残すのは件数だけ。
  `residency.viewed`（DECISIONS #261）と同じ扱いで、記録の口を
  **値を受け取れない形**にすること。
- **削除済みの在留資格の情報を監査ログから復元できる形にしない。**
  監査ログが「消したはずの情報」の控えになってはならない。
- **件数は、その瞬間に DB に実在した削除対象行数**（hotfix #268）。
  アプリケーション側が数えた候補数を渡さない。選定から DELETE までの間に
  別経路で消えている行がありうる。
- 対象が塊に分かれた場合、**監査ログは塊ごとに 1 行**でよい。
  **合計が実際の削除総数**になること。
- 監査ログの INSERT は `audit.ts` が組み立てる（`auditCountStatement()`）。
  **`residency.ts` から `auditLog` へ直接 INSERT しない。**

### 実装前に別途確かめること

- **バックアップや退避データに残る期間と、そこからの削除方法。**
  D1 のバックアップ、`ARCHIVE` の退避（PK-SPEC-P0 §19.7）に在留資格が
  含まれるかを確かめ、含まれるなら消し方を決めてから実装する。

## やらないこと

- **在留カード番号の保存**（列を作らない。INV-08 v2 の趣旨に反する）
- 削除の取り消し（復元の経路を作らない）
- 退職の判定そのものの変更（`workStatus` の扱いは P8-01 のまま）
- **保存期間を設定で変えられるようにすること**（PK-IMPL-CONTRACT §11.4 の
  「設定可能にすると運用中の判断でいずれ変更される」と同じ理由。
  変更にはリリースを要する状態を保つ）
