## 背景
プロトタイプ 07 は「登録 31 名・稼働中 28 名・研修中 3 名・在留期限 90 日以内 2 名」の
KPI と、スタッフ一覧（**お名前 / 言語 / 経験 / 主な担当施設 / 在留期限 / 状態**）を持つ。
在留資格そのものは P8-02、研修は P8-10 が担当し、**ここは台帳の骨と一覧まで。**

## やること

### `staff_pay_profile` に列を足す（**新しい表を作らない**）
`packages/db/src/schema/payout.ts` の docstring が既にこう書いている。

> `staffPayProfile` は P8-01 `staffProfile` の**先行サブセット。**
> P8-01 実装時はこの表を包含・拡張する（別の台帳を並べない）。

これに従う。`membershipId` で 1 スタッフ 1 行という形は既にできており、
仕様 §1.3 の `staffProfile` と**主キーの粒度が同じ。** 表を 2 つ並べると
「どちらが在籍の正か」が生まれる。

**足す列**（すべて後方互換。既存行は `NULL` / 既定値で通る / architecture.md §6）

| 列 | 備考 |
|---|---|
| `hiredOn` / `resignedOn` | `YYYY-MM-DD`。「経験 5 年目」はここから導く |
| `workStatus` | `ACTIVE` / `TRAINING` / `ON_LEAVE` / `RESIGNED`。既定 `ACTIVE` |
| `languages` | JSON 配列。プロトタイプの「言語」列と「言語の構成」表 |
| `skills` | JSON 配列。P8-04 が使う |
| `note` | |

**`isActive` と `workStatus` を混ぜないこと。** `isActive` は「支払の対象か」で、
`workStatus` は「いま働いているか」。休職中でも前月分の支払は残る。

**足さない列と理由**（同じ事実を 2 か所に置かない）:
- `displayName` / `staffNumber` → `user` が持つ
- `employmentType` → この表が既に持つ
- `hourlyRate` / `perRoomRate` → `payRule` が持つ（解決順序つき）。
  **プロトタイプ 07 の一覧に単価の列が無い**
- `healthCheckedOn` / `trainingCompletedOn` → P8-10（研修と資格）

**表の名前は変えない。** 列の削除・リネームを 1 リリースで行わない
（architecture.md §6）。名前が支払寄りに見える点は docstring で補う。

### 画面 `/app/staff`
- KPI 4 枚: 登録 / 稼働中 / 研修中 / 在留期限 90 日以内（最後の 1 枚は P8-02 が埋める）
- 一覧: お名前 / 言語 / 経験 / 主な担当施設 / 在留期限 / 状態
- 「🌐 言語の構成」（言語 / 人数 / バー）
- 絞り込み: 全員 / 稼働中 / 研修中（プロトタイプのセレクトと同じ 3 つ）

## やらないこと
- 住所・生年月日・本籍・マイナンバー・口座情報の列（security.md §3 / 受け入れ基準）
- **単価の列**（プロトタイプに無い。単価は `payRule` と支払集計の画面）
- 個人ランキング・最速比較・自動評価（CLAUDE.md §4 / security.md §5）
- 出勤打刻（DECISIONS #221 で見送り）
