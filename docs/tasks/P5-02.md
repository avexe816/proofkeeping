**完了条件について**

  （FLOOR / CEIL / ROUND）を `POST` と `PATCH` の両方で受ける。
- 請求先メール（必須）と CC（`MAX_CC_EMAILS = 10`）を受ける。
  画面はカンマ区切りで入力し、空要素を落として配列にする。

**止まらずに判断したこと**

- **削除の口を作らなかった。** 取引を終えた相手は `isActive = false`
  （PK-SPEC-P0 §24.4 と同じ方針）。過去の請求書が `counterpartyId` で
  参照しているため、行を消すと帳票から相手が辿れなくなる。
  `DELETE` は Hono に登録していないので 404 になる（テストで固定）。
- **取引先コードは登録後に付け替えられない**（DECISIONS #122）。
  `upsertCounterparty()` が引くのは `uq_cp`（組織 × コード）で、別の
  コードを送ると更新ではなくもう 1 件が生まれる。`PATCH` は 400 を返し、
  画面はコード欄を `readOnly` にする。
- **`POST` で既存コードに当たったら 409。** リポジトリの upsert は
  コード一致で更新へ落ちるが、`POST` の意図は「作る」なので黙って
  上書きしない。
- **`isQualifiedIssuer` は API 側で導く**（登録番号の有無）。画面に
  判定を持たせない（billing.md §1）。登録番号は `T` + 13 桁の**形式
  だけ**を見る。実在の照会は国税庁側で、ここからは行けない。
- 監査ログに `counterparty.created` / `counterparty.updated` を足した
  （security.md §6 の列挙は「施設・客室マスタ」までだが、取引先は
  帳票のスナップショット元 / billing.md §6）。
