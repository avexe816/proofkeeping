**完了条件について**

- 5 段階（§3.2）は `PRICING_STAGES` が並び順そのもの。`matchStage()` が
  規則 1 件の段を返し、`resolvePricing()` が「段が先、同点なら
  `priority` の**小さい**方、なお同点なら `validFrom` が新しい方」で決める。
  API の `GET /resolve` が同じ純粋関数を通した結果を返す。
- 有効期間は `isEffective(rule, date)`。**両端を含む。** `validTo` が
  `null` なら以後ずっと有効。

**止まらずに判断したこと**

- **該当が無いとき `null` を返す。0 を返さない。** 0 円は「無料と決めた」で、
  `null` は「値段が決まっていない」。混ぜると決め忘れが請求書に 0 円として
  静かに載る（§3.2 MUST / billing.md §8）。`GET /resolve` も
  `resolved: null` を返す。
- **更新の口を作らなかった。** 値上げは行の追加。既存の行を書き換えると
  過去の請求書の根拠が変わる。`PATCH` / `DELETE` は 404（テストで固定）。
- **終了は `validTo` だけを書く専用の口**（DECISIONS #123 /
  `POST /:id/close`）。`validFrom` より前へは閉じない（開始前に終わる
  規則は「一度も有効でなかった」ことになり、消せない表の中で消したのと
  同じ状態を作れてしまう）。
- **`GET /resolve` の鍵は全部必須**（400）。欠けたまま引くと
  「当たらなかった」と「引けなかった」が同じ答えになる。
- `listPricingRules()` の `orderBy` を `desc(priority)` から昇順へ直した。
  **P5-01 で仕様と逆に書いていた**（§3.2 は「priority の小さいものを採用」）。
  スキーマのコメントも併せて訂正。
- 監査ログに `pricingRule.created` / `pricingRule.closed` を足した。
