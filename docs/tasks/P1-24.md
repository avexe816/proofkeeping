## この task が起票された理由

`room_type` を**読む**関数（`listRoomTypes()`）は P1-02 / P1-04 / P1-06 の
未達分を実装したときに追加した。しかし**書く経路が一つも無い。**
画面も API も無く、`packages/db/src/seed.ts` が入れたものを読むだけ。

そのため以下が起きる。

| 画面 | seed の無い環境での見え方 |
|---|---|
| W-05 `/app/p/{id}/plan` | 「タイプ」列が全行 `—`（客室タイプが解決できない） |
| W-17 `/app/settings/standard-times` | **表が 0 行。**「客室タイプがまだ登録されていません」だけが出る |
| W-16 `/app/settings/checklists` | 客室タイプ別テンプレートを**作れない**（選択肢が空） |

`standardTime` の一意制約は `(organizationId, propertyId, roomTypeId, taskType)`
で、`checklistTemplate` の第 3 階層も `roomTypeId` を持つ。**客室タイプが
無いと、標準時間の設定とチェックリストの最も具体的な階層が丸ごと使えない。**

`room.roomTypeId` も同様に埋める経路が限られている。P0-22 の CSV 取込は
`room_type_code` 列を読むが、**`PANTRY` という 1 語を `isSellable` の判定に
使うだけ**で、客室タイプのマスタとは突き合わせていない（`rooms.tsx` の
注記「客室タイプのマスタが解決できるまでは、その 1 語だけを見る」）。

## なぜ P1 の後・P2 の前なのか

- **P1 の中に入れない。** P1-19 実機テスト / P1-20 現場検証（★出荷判定）は
  すでに人間の作業として待っている。ここへ画面を 1 つ足すと、検証の
  対象が動く。P1-20 は「自社施設で 2 週間、紙を全廃して運用する」もので、
  自社施設は seed 済み＝客室タイプが入っている状態で回せる。
- **P2 より先に置く。** P2-01（スキーマ: 検査・証跡）以降は検査ポリシーを
  客室タイプ別に持ちうる（PK-SPEC-P2）。**その前に客室タイプを人が
  作れる状態にしておく。**
- CLAUDE.md §9 の「P2 は P1 の現場出荷判定を通過するまで着手しない」は
  この task に掛からない（P2 の task ではない）。ただし**P1-19 / P1-20 の
  検証中にこの task を実装すると検証対象が動く**ので、着手は
  P1-20 の判定後にすること。

## やること

### 1. リポジトリ層（`packages/db/src/repositories/property.ts`）

- `createRoomType(env, ctx, input)` — `generateId(ctx.orgShortId, "rtyp")`。
  `code` は施設内で unique（`uq_room_type_property_code`）。
- `updateRoomType(env, ctx, roomTypeId, input)` — `name` / `bedCount` /
  `capacity` / `sortOrder` / `isActive`。
- `findRoomTypeById(env, ctx, roomTypeId)`。
- `listRoomTypes()` に `isActive` の絞り込みを足す（**いまは有効なものだけを
  返す**。設定画面は無効化済みも見せる必要がある）。
- `countRoomsByRoomType(env, ctx, propertyId)` — 無効化のときに
  「この客室タイプが割り当てられた客室が N 室あります」を出すため。

### 2. 客室への割り当て

- `updateRoom()` に `roomTypeId` を足す（`UpdateRoomInput` にまだ無い）。
- P0-22 の CSV 取込（`parseRoomCsv` の `room_type_code`）を客室タイプの
  マスタと突き合わせる。**マスタに無いコードは客室タイプ未設定として
  取り込み、コードを応答で返す**（1 行の誤りで全体を落とさない / P1-04 の判断 1）。
  `PANTRY` を `isSellable = false` に写す既存の扱いは**変えない。**

### 3. 画面（`/app/settings/room-types`）

`nav.propertySettings`（いまは `PLANNED`）の一部として置くか、
`/app/settings/rooms` の中に節を足すかを実装時に決める。
**決めたら DECISIONS に残すこと。**

- 施設ごとの一覧（`code` / `name` / `bedCount` / `capacity` / 客室数）。
- 追加・編集。**無効化のみ。物理削除の口を作らない**（CLAUDE.md §4）。
- 無効化のときに、その客室タイプが割り当てられた客室の件数を提示して
  明示操作を求める（PK-SPEC-P0 §24.5 と同じ形。`rooms.tsx` の
  `confirmDeactivate` が先例）。
- 客室一覧から客室タイプを付け替えられること（W-05 のタイプ列が埋まる）。

### 4. API（`/api/v1/room-types`）

- `GET /api/v1/room-types?propertyId=`
- `POST /api/v1/room-types`
- `PATCH /api/v1/room-types/:roomTypeId`
- 権限は `property.read` / `property.write`（**新しい action を足さない。**
  客室タイプは施設マスタの一部で、`PERMISSION_ACTIONS` に行を足す根拠が
  security.md §1 に無い）。
- 状態変更は `Idempotency-Key` に対応する（CLAUDE.md §5）。
- 作成・更新・無効化は `recordAudit()`（security.md §6 の
  「施設・客室マスタの作成・更新・無効化」）。`action` は `property.updated` /
  `property.created`。

### 気づいたこと

1. **`UpdateRoomInput.roomTypeId` は既にあった。** この task ファイルの
   「`updateRoom()` に `roomTypeId` を足す（まだ無い）」は誤り。

2. **`createFakeD1()` が `meta.changes` を返していなかった。**

3. **`room_type` の越境テストは `findById` を施設 ID で代用していた。**

   やっていた形）。`findRoomTypeById()` に差し替えた。
4. **`INSERT` は共通スイートに載せられない。** `describeTenantIsolation()` の

   採番される ID の `orgShortId`）。

### 申し送り

- **`code` は編集できない。** CSV 取込と P6 の `externalMapping` が突き合わせる
  鍵で、変えると過去の取込が別のタイプを指す。打ち間違えたら無効化して
  作り直す。画面にも API にも `code` の更新経路を置いていない。
- **CSV の突き合わせは大小を無視する**（`twn` と `TWN` は同じ）。一方
  `uq_room_type_property_code` は大小を区別するので、**大小違いの 2 件を
  登録できてしまう。** その場合は先に登録したほうが CSV で選ばれる。
  制約を `COLLATE NOCASE` にするかは破壊的変更なので手を付けていない。
- **`PANTRY` → `isSellable = false` の扱いは変えていない。** 突き合わせの
  成否と結びつけていないので、マスタに `PANTRY` を登録していない施設でも
  清掃専用の場所の判定は従来どおり効く。
- **無効化しても客室の `roomTypeId` は外れない。** 標準時間と
  チェックリストの設定も残る。選択肢に出なくなるだけ（§24.5 の向き）。
