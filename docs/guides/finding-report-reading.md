# 差異レポートの読み方

**版**: v1.0（2026-08-15）
**対象**: オーナー / 運営管理者 / 施設責任者 / 監査閲覧
**仕様**: docs/PK-SPEC-P7.md §7.3 / docs/PK-SPEC-P4.md §6

> **この文書は Audit モジュールの利用条件です。**
> 有効化のとき、この内容への同意を求めます（§7.3 MUST）。
> 同意した版数は組織の記録として残ります。

---

## 0. 3 行で

1. 差異は **「3 系統の記録が食い違っている」という事実**だけを指します。
2. 原因は現場・設備・データ取込・ルールの側にもあります。**判断は人が行います。**
3. **人事上の措置に直接使わないでください。** そのための道具ではありません。

---

## 1. 差異は「食い違い」であって、誰かの行為を裏づけるものではありません

ProofKeeping は 3 系統の記録を突き合わせます。

| 系統 | 中身 | 出どころ |
|---|---|---|
| ① 稼働記録 | 稼働・空室、予約参照番号、人数 | PMS / CSV 取込 / 公開 API |
| ② 現場の記録 | ベッドの使用台数、ゴミの量、タオルの枚数 | 清掃スタッフの入力（M-05） |
| ③ 物理信号 | 解錠の時刻 | スマートロック等の連携 |

差異レポートに出るのは、**この 3 つが揃わなかった組み合わせ**です。
それ以上のことは書かれていませんし、書けません。

現場の記録は「見たもの」しか集めていません。
清掃スタッフには「この部屋は使われましたか」と聞かず、
**「ベッドはいくつ使われていましたか」**と聞いています（PK-SPEC-P3 §1.2）。
解釈と突き合わせはサーバー側で行うため、差異の有無は現場の主観を含みません。
同時に、**現場の入力は差異の原因を説明しません。**

## 2. 差異には多様な原因があります

同じ差異が、まったく違う理由で立ちます。

| よくある原因 | 例 |
|---|---|
| 運用上の例外 | 当日アップグレードで部屋を移した／設備確認で入室した |
| 記録の欠落 | 予約が PMS 側で取り消され、取込が追いつかなかった |
| 取込の遅延 | 稼働記録が夜間バッチで届き、清掃時点では空室だった |
| 機器の不調 | スマートロックの時刻ずれ、電池切れによる信号の欠落 |
| 基準値のずれ | 客室タイプを変えた直後で、消耗の基準値がまだ学習中 |
| ルールの感度 | 閾値がその施設の運用に合っていない |

**「原因が分からない」も正当な結果です。**
分からないまま閉じる場合は「その他」の解決コードを選び、
何を確認したかをメモに残してください。

## 3. 必ず個別の事実確認を行ってください

差異レポートは**確認の入口**です。出発点であって、結論ではありません。

確認の順序をおすすめします。

```
1. 差異詳細（W-07）で 3 系統の生の記録を見る
     → どの系統が欠けているのか、ずれているのかを特定する
2. 参考情報を見る
     → 清掃写真の枚数・入室記録・前後の稼働・客室状態
3. 現場に「その日の状況」を聞く
     → 差異の内容ではなく、その日その部屋で何があったかを聞く
4. 解決コードを選んで閉じる
```

**3 を飛ばさないでください。** 画面に写っていない事情は、必ずあります。

## 4. 人事上の措置に直接使用しないでください

差異レポートは**内部統制の支援**を目的とした機能です。
個人の評価・処遇・懲戒の根拠として使う設計になっていません。

製品側で、次のようにしてあります。

- 個人ランキング・最速比較・自動評価の画面を持ちません。
- 個人単位の指標は、対象期間 20 タスク未満なら表示しません。
- `CLEANER` と `INSPECTOR` は差異レポートに到達できません。
  （メニューに出ないだけでなく、URL を直接開いても見えません）
- 差異には清掃担当者名を主語にした文言を出しません。

**顧客側の運用でも、同じ線を引いてください。**
利用規約で、スタッフへの記録取得の周知をお願いしています（§6.3）。

## 5. 確信度の意味

差異には 0〜100 の**確信度**が付きます。

**確信度は「根拠の強さ」であって、「不適切な行為の確からしさ」ではありません。**

| 上がる要因 | 下がる要因 |
|---|---|
| 複数の系統が同じ向きに食い違っている | 現場の記録が既定値のまま確定されている（−20） |
| 物理信号が裏づけている | 基準値がまだ学習中（`isReliable` でない） |
| 前後の稼働と整合しない | 系統そのものが未接続（データなし） |

確信度 90 の差異が「ほぼ確実に問題がある」を意味することはありません。
**「3 系統がはっきり食い違っている」以上の意味を読み取らないでください。**

重要度（高 / 中 / 低）は**確認の順番**を決めるためのものです。
施設ごとに引き下げられます（W-25 ルール設定）。

## 6. 「対象外」として閉じることの重要性

差異には 5 つの状態があります。

| 表示 | 意味 |
|---|---|
| 未対応 | まだ誰も見ていない |
| 確認中 | 担当者が確認を始めた |
| 対応済 | 事実を確認し、結論を出した |
| 対象外 | 記録・ルール・基準値の側に理由があった |
| 抑制 | 点検の登録・自社利用・販売停止など、あらかじめ説明がつく条件 |

**「対象外」で閉じることは、後ろ向きな作業ではありません。**
閉じるときに選ぶコード（ルールの感度が高すぎる / 基準値が実態に合わない /
データの誤り）が、そのままルール設定と基準値の調整材料になります。

対象外が多い状態を放置すると、本当に確認したい差異が埋もれます。
**月に 1 回、対象外のコードの内訳を見て、閾値を調整してください。**

閉じるときの解決コードは次のとおりです。

| 分類 | コード |
|---|---|
| 対応済 | 運用上の例外 / 記録の欠落 / 取込の遅延 / 機器の不調 / 手順を改善した / 差異を確認し社内で対応 / その他 |
| 対象外 | ルールの感度 / 基準値のずれ / データの誤り / その他 |

## 7. 現場スタッフへの説明方法

**説明しないまま運用しないでください。** 説明の有無で、記録の質が変わります。

現場に伝えていただきたいのは、次の 3 点です。

> 1. 記録は、清掃の品質管理と業務改善、請求の根拠のために使います。
> 2. **速さや件数で個人を比べることはしません。** 順位も出しません。
> 3. **見たままを入れてください。** 「こう答えたほうがよさそう」と
>    考える必要はありません。判断はシステム側で行います。

現場が「記録が自分の評価に使われる」と受け取った時点で、
正確な記録より見た目のよい記録を選ぶ動機が生まれます。
そうなると差異レポートの入力データとしての価値が失われ、
**この機能は動かなくなります。**

清掃スタッフ向けの説明は、`cleaner-guide.html`（A4 1 枚・日英）に
そのまま印刷できる形で入っています。休憩室に貼ってご利用ください。

---

## 8. この機能を止めたいとき

Audit モジュールは、いつでも無効化できます。
無効化しても、これまでに記録された清掃・検査・観察の記録は残ります。
差異レポートの画面と API に到達できなくなるだけです。
