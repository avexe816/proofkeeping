0. 本フェーズの目的
0.1 一行目標
社内試験運用から、外部有償顧客が自力で導入・運用できる製品へ移行する。

M1〜M11 は「作る」フェーズだった。M12 は「売れる状態にする」フェーズ。機能追加ではなく、セルフサービス化・運用体制・信頼性の確立に注力する。

0.2 GA の定義
以下をすべて満たしたとき General Availability とする。

有償顧客 5 社が同時稼働している。

うち 2 社以上が営業支援なしで自力導入した。

月間稼働率 99.5% 以上を 1 か月継続。

清掃時間帯（06:00–20:00）の稼働率 99.9% 以上。

サポート問い合わせが 1 社あたり月 3 件以下。

障害発生時の復旧手順が文書化され、実際に訓練済み。

4.4 テナント移送
特定シャードが逼迫した場合、テナント単位で別シャードへ移す。

text
1. 対象テナントを読み取り専用にする
2. 全テーブルを新シャードへコピー
3. 行数とチェックサムを照合
4. ルーティングテーブルを更新（組織 → シャード の明示マッピング）
5. 読み書きを再開
6. 旧シャードのデータを削除
MUST: ハッシュベースのルーティングを、明示マッピングで上書きできる仕組みを用意する。

ts
// 明示マッピングを優先する
// SHARD_MAP は明示マッピング専用の KV namespace。TTL を設定しない。
// 失効すると下の fnv1a32 に無警告で落ち、移送済みテナントのデータが分裂する。
// architecture.md §1 / DECISIONS.md #004
export async function resolveShard(env: Env, organizationId: string) {
  const override = await env.SHARD_MAP.get(`shard:${organizationId}`);
  if (override) return Number(override);
  return fnv1a32(organizationId) % SHARD_COUNT;
}

5. 可用性と障害対応
5.1 稼働率目標
text
全体:               99.5% / 月
清掃時間帯（06-20）: 99.9% / 月
5.2 縮退運転
障害時にすべてを止めない。優先順位を定める。

優先度	機能	障害時の扱い
1	清掃タスクの参照・開始・完了	何があっても維持する
2	写真アップロード	オフラインキューで吸収
3	検査	一時的に「検査なし」へフォールバック可
4	客室ボード	更新頻度を落とす
5	照合バッチ	遅延して実行
6	PDF 生成	キューに滞留させる
7	外部連携	停止して手動 CSV へ
MUST: 優先度 1 の機能は、D1 の書き込みが失敗してもオフラインキューに保持し、復旧後に送信する。
