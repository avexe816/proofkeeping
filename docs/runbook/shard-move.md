# シャード移送手順

**版**: v1.0（2026-08-15）
**対象**: 社内（運用者）
**仕様**: docs/PK-SPEC-P7.md §4.4 / 実装: `scripts/tenant-move.ts`・`packages/db/src/tenantMove.ts`

特定のシャードが逼迫したとき、**テナント単位**で別シャードへ移す。

> **この操作は取りこぼしがそのままデータ消失になる。**
> CLI の既定は `--plan`（何も触らない）。手順 4・6 は自動化していない。

**`pnpm` はリポジトリルートで実行する**（`deploy.md` 冒頭「実行位置」）。

---

## 0. 前提

- 対象組織を**読み取り専用にできる時間**を確保する。夜間が望ましい。
- 移送先のシャードの空きを確認する（`pnpm shards:usage --env production`）。
- **移送は 1 組織ずつ。** 複数を並行させない。

---

## 1. 全体（§4.4 の 6 手順）

```
 ① 対象テナントを読み取り専用にする        人が行う（自動化していない）
 ② 全テーブルを新シャードへコピー          pnpm shards:move --copy
 ③ 行数とチェックサムを照合                pnpm shards:move --verify
 ④ 明示マッピングを書く（SHARD_MAP）       人が行う（CLI が値を出力する）
 ⑤ 読み書きを再開                          人が行う
 ⑥ 旧シャードのデータを削除                人が行う
```

**手順 2・3 だけを自動化してある**（DECISIONS #162）。
手順 1 が自動化できない以上、**照合が通った時点のデータが最新である保証が無い。**
その保証を人が作ってから、人が書く。

---

## 2. 手順

### ① 読み取り専用にする

現時点で「組織を読み取り専用にする」スイッチは実装されていない。
**運用で止める。**

1. 対象組織に事前連絡する（清掃時間帯を避ける）。
2. 停止時間帯に入ったことを確認する。
3. **その時間帯に書き込みが来ないことを確かめてから ② へ進む。**

> 書き込みが続いたまま ② を始めると、コピーの取りこぼしが
> ③ の照合をすり抜けることがある（コピー中に増えた行は
> コピー元・コピー先の両方で数えられない）。

### ② コピー

```bash
pnpm shards:move --env production --org <organizationId> --to 09 --plan
# 何をするかだけ出る。**触らない。** まずこれを読む

pnpm shards:move --env production --org <organizationId> --to 09 --copy
```

**移す表は `sqlite_master` から取る**（schema からではない）。
移してはならない表は `schema_version` と `org_directory` の 2 つだけで、
**知らない表は「移す側」に倒してある。** 新しい表を足した人が
移送のことを忘れても、データが置き去りにならない向き。

### ③ 照合

```bash
pnpm shards:move --env production --org <organizationId> --to 09 --verify
```

**行数とチェックサムの両方**を突き合わせる。1 つでも合わなければ ④ へ進まない。

合わない場合:
1. ① に戻り、書き込みが本当に止まっていたかを確認する。
2. 移送先の該当組織の行を消してから ② をやり直す。
3. **移送元には手を付けない。** 元が正である。

### ④ 明示マッピングを書く（人が行う）

CLI が書くべき値を出力する。**それを人が KV へ書く。**

```bash
pnpm --filter @pk/web exec wrangler kv key put \
  --binding SHARD_MAP "shard:<organizationId>" "9" --remote
```

**`wrangler` はルートでは通らない**（ルートに wrangler が無く、`wrangler.toml` は
`apps/web/`）。`--filter @pk/web exec` を通すとルートに居たまま実行できる。

**`--expiration-ttl` を付けないこと。**
TTL で失効すると `resolveShard()` は `fnv1a32` のフォールバックへ
**無警告で落ちる。** 移送済みの組織なら、以後の読み書きが移送前の
シャードへ向かい、**同一テナントのデータが複数シャードに分裂する。**
この破損は静かに進行し、発見が遅れる。

値の形は `assertShardMapValue()` が定める（`0`〜`SHARD_COUNT-1` の 10 進数）。

### ⑤ 再開

1. 対象組織で 1 件、読み取りと書き込みを試す。
2. `pnpm shards:usage --env production` で移送先の使用率が増えたことを確認する。
3. 組織へ再開を連絡する。

### ⑥ 旧シャードのデータを削除（人が行う）

**すぐに消さない。** ⑤ の再開から**最低 1 業務日**は残す。

消す前に確認すること。

- ④ の明示マッピングが読めること（`wrangler kv key get`）。
- 対象組織の読み書きが移送先へ向かっていること。
- 移送先に当日の新しい行が積まれていること。

確認できたら、旧シャードから対象組織の行を削除する。

---

## 3. 途中で止めるとき

| 中断した段階 | 状態 | 戻し方 |
|---|---|---|
| ② の途中 | 移送先に半端な行がある | 移送先の該当組織の行を消す。**元は無傷** |
| ③ で不一致 | 同上 | 同上。② からやり直す |
| ④ の直後 | 読み書きが移送先へ向いている | `SHARD_MAP` のキーを**削除**すれば既定の計算へ戻る。ただし④以降に書かれた行は移送先にしか無い |
| ⑥ の後 | 旧シャードにデータが無い | **戻せない。** Time Travel（`recovery.md`）で旧シャードを戻す |

**④ を跨ぐと戻すのが難しくなる。** ここが分水嶺。
