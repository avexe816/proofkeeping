## 障害のときに開く順番

```
1. incident-response.md §0     まず /api/health を見る
2. incident-response.md §1〜2  症状から辿る
3. recovery.md                 データを戻す必要があるとき
4. oncall.md                   上げる先と告知の判断
```

**deploy.md と shard-move.md は平常時に読む文書。**
障害の最中に初めて開かないこと。

## この文書群の「合否」

§7.2 の完了条件は 2 つ。

| 条件 | 状態 |
|---|---|
| システム概要書が電子帳簿保存法の備付け要件を満たす | **満たしている**（`system-overview.md` §1 の対応表） |
| 障害対応手順で実際に対応できた | **未確認。人が確かめる**（P7-14 の復旧訓練と同じ性質） |

2 つ目は書いただけでは満たせない。**復旧訓練（P7-14）で、
この文書を読んだだけの担当者が質問なしで完了できるかを見る。**
詰まった箇所はその場で追記する。訓練の記録は `recovery.md` §5。

## 書くときの決まり

- **未実装・未作成のものを「ある」と書かない。**
  この製品にはまだ埋まっていない前提が複数ある（`deploy.md` §7）。
  手順書が実態より進んでいると、障害の最中に嘘を読むことになる。
- **実在しない連絡先を書かない。** 枠を置いて「（未記入）」とする。
- 顧客向け文書と同じ語彙で書く（`.claude/rules/ui-writing.md` §2）。
  CI は `tests/docs/runbook.spec.ts` で走査する。

内部文書なので、機械の状態を述べる語（障害・停止・滞留）は使ってよい。
避けるのは**人の行いを評する語**のほう。
