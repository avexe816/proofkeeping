# 運営担当者の初期開通（1 人目だけ）

**版**: v1.0（2026-08-21）
**task**: docs/tasks/PF-16.md
**決定**: docs/DECISIONS.md #240（オーナー判断）・#245（実装）
**関連**: `.github/workflows/platform-bootstrap.yml` / `deploy.md` §3.5

運営コンソール（`/plat/*`）に**最初の 1 名**を作る手順。
**2 人目以降はこの手順を使わない**（§7）。

---

## 0. 3 分で読む要約

```
① Actions → platform-bootstrap → 環境・メール・表示名を入れて実行
② 本人のメールに開通リンクが 1 通届く（30 分で切れる・1 回だけ使える）
③ 本人がリンクを開いてパスワードを設定する
④ そのまま認証アプリを登録し、復旧コードを保管する
⑤ ここまで終わって初めて /plat/* に入れる
```

**押した人の画面に開通リンクは出ない。** 受け取れるのは宛先の本人だけ。

---

## 1. 前提の確認（**実行前に必ず見る**）

| 確認すること | 見かた | 満たないとどうなるか |
|---|---|---|
| 対象環境が合っている | 実行画面の `environment` | **本番に運営担当者ができる。取り消せない** |
| migration が当たっている | `staging-bootstrap.yml` の `phase=migrate --check` | `platform_bootstrap_token` が無く 500 |
| `RESEND_API_KEY` が登録済み | `wrangler secret list --env <env>` の名前 | `DELIVERY_REJECTED` で**何も作られない** |
| `TWO_FACTOR_ENCRYPTION_KEY` が登録済み | 同上 | パスワードは設定できるが**2FA 登録で詰まる**（PF-17） |
| 運営担当者がまだ 0 名 | 実行して `OPERATOR_EXISTS` が出なければ 0 名 | 押しても拒否される（害は無い） |
| 宛先のメールが受け取れる | 本人に確認する | 30 分後に券が切れ、発行から実行し直しになる |

**`secrets-and-seed` を再実行しないこと。** `SESSION_SECRET` が回り、
既存のセッションが全部切れる。足りない秘密は 1 つずつ入れる
（`secret-2fa` phase / DECISIONS #244）。

---

## 2. 実行する（発行）

GitHub → **Actions** → **platform-bootstrap** → **Run workflow**。

| 入力 | 値 |
|---|---|
| `environment` | `staging` または `production`。**ここを間違えない** |
| `email` | 最初の運営担当者のメールアドレス（開通リンクの宛先） |
| `display_name` | 運営コンソールに出る表示名 |
| `confirm` | `BOOTSTRAP` |

実行すると、workflow は次の順に動く。

1. 対象の Worker 名と `APP_BASE_URL` を読み上げる（**ここで環境を目視確認する**）
2. 1 回きりの管理鍵を作って登録し、再デプロイする
3. 開通の口を **1 回だけ**叩く
4. **必ず管理鍵を削除して**再デプロイする（失敗しても消える）

ログに出るのは「送信しました」と有効期限だけ。
**開通リンクも管理鍵も出ない**（§6）。

---

## 3. 開通リンクからパスワードを設定する（本人の作業）

1. 届いたメールのリンクを開く。`/plat/bootstrap/...`
2. 表示名とメールアドレスが自分のものであることを確かめる
3. 新しいパスワードを 2 回入力する
   - **10 文字以上、英大文字・英小文字・数字をそれぞれ含む**
   - 使い回さない。パスワード管理ソフトで生成することを勧める
4. 「パスワードを設定する」を押す

**リンクは 1 回で無効になる。** 押した直後に画面を閉じてしまっても、
アカウント自体はできている（**`/plat/login` から入り直せる**）。
設定の前に閉じた場合は、券が生きている 30 分の間なら同じリンクで再開できる。

---

## 4. 認証アプリの登録と復旧コードの保管（**ここまでやって完了**）

パスワードを設定すると、そのまま 2 段階認証の登録画面に進む。

1. 認証アプリ（Google Authenticator / 1Password / Authy など）で QR を読む
   - 読めないときは画面下のキーを手入力する
2. アプリに出た 6 桁を入力して「登録を確定する」
3. **復旧コード 10 本が 1 回だけ表示される**
   - 印刷するか、パスワード管理ソフトの安全なメモへ保存する
   - **この画面を閉じると二度と表示されない**（再表示の経路は作っていない）
   - 足りなくなったら `/plat/2fa/recovery` で再発行する（**古い分は無効になる**）
4. 「運営コンソールへ進む」

**ここまで終わるまで `/plat/*` は 404 を返す。**
パスワードだけの状態では、稼働状況もテナント一覧も開けない。

## 5. 開通できたことの確認

| 見ること | 期待 |
|---|---|
| `/plat/login` でログインできる | メール＋パスワード → 6 桁 → `/plat/status` |
| 未ログインで `/plat/status` | **404**（`/login` へ飛ばさない / DECISIONS #230） |
| もう一度 workflow を押す | **`OPERATOR_EXISTS` で失敗する**（1 人目の経路が閉じたことの確認） |

---

## 6. token と鍵をログへ出さないこと

**この手順で扱う秘密は 4 つ。どれも記録に残さない。**

| 秘密 | どこにあるか | 守り方 |
|---|---|---|
| 開通 token | メール 1 通の中のリンクだけ | DB はハッシュのみ。応答にも監査ログにも出ない |
| パスワード | 本人がブラウザで入力する | 保存されるのは PBKDF2 のハッシュだけ |
| TOTP secret | 登録画面と認証アプリの中 | DB は暗号化した封筒（DECISIONS #244） |
| 復旧コード | 1 回きりの表示 | DB は SHA-256 のみ |

**やってはいけないこと。**

- 開通リンクを Slack・チケット・PR・メモへ貼る（**メールから直接開く**）
- 管理鍵（`PLATFORM_BOOTSTRAP_TOKEN`）を控える・使い回す
- workflow に `set -x` を足す（鍵が展開されてログに残る）
- 開通リンクを workflow summary や artifact に出す
- 復旧コードを平文で共有ドライブに置く

これらは `tests/security/platformBootstrap.spec.ts` が
**コードと workflow の側で**塞いである。手順の側でも守ること。

---

## 7. 2 人目以降はこの手順を使わない

この経路は**運営担当者が 0 名のときしか通らない**（1 名でも居れば拒否）。
2 人目以降は PF-14 の招待画面が持つ。**まだ実装されていない**ので、
それまでは 1 名で運用する。

「1 人目を作り直したい」ときも、この手順では作り直せない。
既存の担当者を無効化（`status = SUSPENDED`）しても**行は残る**ため、
bootstrap は拒否のままになる。**運営担当者を消す口は用意していない**
（監査ログの参照先を消さないため）。

---

## 8. 失敗したときに、再実行の前に確かめること

**まず出た `error` を読む。** 押し直してよいかはそれで決まる。

| 出力 | 意味 | 押し直す前に |
|---|---|---|
| `OPERATOR_EXISTS` | 既に運営担当者が居る | **押し直さない。** 誰が居るのかを先に確かめる（§7） |
| `DELIVERY_REJECTED` | 開通リンクを渡せなかった | **有効な券は残っていない**（作られていないか、失効させた）。下の 3 点を順に確かめてから押す |
| `INVALID_REQUEST` | メールか表示名の形式 | 入力を直して押す |
| HTTP 404 | 管理鍵が載っていない | 前回の実行が途中で落ちて鍵が消えている。**そのまま押し直してよい** |
| 何も届かない | 送信は成功している | 迷惑メールを見る。30 分を過ぎていたら押し直す |

**押し直しは安全。** 新しい券を出すとき、**未使用の古い券はすべて失効する**
（有効な開通リンクが 2 本同時に存在しない）。

### `DELIVERY_REJECTED` のときに確かめる 3 点

**応答はどちらか（経路が未設定 / 送信に失敗）を教えない。**
分けて返すと、この無認証の口が「この環境はメール送信が未設定」を
答える装置になるため、**わざと 1 種類にしてある**（DECISIONS #246）。
運用者は順に確かめる。

```
1. RESEND_API_KEY が対象環境に登録されているか
   wrangler secret list --env <env>   ← **名前だけを見る。値は出さない**
2. 宛先の綴りが正しいか
3. Resend 側の送信ドメインと差出人が有効か
```

**内訳は残っている。** `platform_audit_log` の `detail.cause` に
`DELIVERY_NOT_CONFIGURED`（経路が無い）か `DELIVERY_SEND_FAILED`
（送信に失敗）が入る。§7 の引き方で読める。**この列に
`RESEND_API_KEY` の値も宛先のメールアドレスも入らない。**

**押し直す前に必ず見ること。**

```
1. どの環境に対して実行したのか（前回のログの「Worker 名」）
2. 管理鍵が残っていないか（wrangler secret list に
   PLATFORM_BOOTSTRAP_TOKEN が居ないこと）
3. 運営担当者ができていないか（/plat/login でメールを入れて
   ログインを試す — できるなら開通は成功している）
```

3 が「できる」なら、**押し直さずに §4 の続き（2FA 登録）から進める。**
パスワードは設定済みなので、ログインすれば登録画面に着く。

## 9. 実行後に残ってはいけないもの

```bash
# **wrangler は apps/web でしか通らない**（wrangler.toml がそこにある）。
cd apps/web

# 管理鍵が消えていること（名前が出ないこと）
wrangler secret list --env <env> | grep PLATFORM_BOOTSTRAP_TOKEN
```

workflow は `if: always()` で削除するが、**runner が落ちた場合は残る。**
名前が出たら手で消し、再デプロイする。

```bash
wrangler secret delete PLATFORM_BOOTSTRAP_TOKEN --env <env>
CLOUDFLARE_ENV=<env> pnpm build
wrangler deploy

cd "$(git rev-parse --show-toplevel)"
```

**鍵が残っている間、開通の口は開いたまま。** 運営担当者が既に居れば
`OPERATOR_EXISTS` で拒否されるが、**開通前なら誰でも押せる状態**になる。
