# 復旧手順

**版**: v1.0（2026-08-15）
**対象**: 社内（運用者）
**仕様**: docs/PK-SPEC-P7.md §5.5

**この手順書だけで実際に戻せることを、四半期に 1 回確かめる**（§5.5 MUST / P7-14）。
訓練の結果はこの文書に追記する。

**`pnpm` はリポジトリルートで実行する**（`deploy.md` 冒頭「実行位置」）。

---

## 0. 目標

| 指標 | 目標 |
|---|---|
| RPO（データ損失の許容） | 1 時間 |
| RTO（復旧までの時間） | 4 時間 |

**RPO 1 時間は「1 時間ぶん失ってよい」ではなく「それ以上失ってはならない」。**
判断に迷ったら、失う側ではなく時間をかける側を選ぶ。

| 対象 | 手段 | 遡れる範囲 |
|---|---|---|
| D1 | Time Travel | 過去 30 日の任意時点 |
| R2 | バージョニング | 誤削除から 30 日 |
| KV | 無し（セッションのみ） | 再ログインで復旧 |

## 1. 最初に決めること

```
        データが失われた / 壊れた
                  │
                  ▼
      ┌───────────────────────────────┐
      │ 失われたのは D1 か R2 か       │
      └───────┬───────────────┬───────┘
              │               │
             D1              R2
              │               │
              ▼               ▼
        ┌───────────┐   ┌──────────────┐
        │ §2 へ     │   │ §3 へ        │
        └───────────┘   └──────────────┘
```

**両方に見える場合は D1 を先に戻す。** R2 のオブジェクトは D1 の行から
参照されており、行が無ければ辿れない。逆（R2 だけ戻す）は
「画面には出るのに開けない」状態を作る。

## 2. D1 — Time Travel

### 2.1 まず時点を決める

**「いつまで正しかったか」を先に確定する。** 復元は時点指定なので、
これが決まらないと始まらない。

- 誤操作なら、その操作の**直前**。監査ログ（`AuditLog`）に時刻がある。
- 不具合の混入なら、そのデプロイの**直前**（`deploy.md` の履歴）。
- **迷ったら遡りすぎない。** 戻しすぎると正しい記録まで消える。

### 2.2 影響範囲を決める

D1 の Time Travel は**データベース単位**で戻る。
つまり**そのシャードに載っている全組織が同時に戻る。**

```
壊れたのは 1 組織か
   │
   ├─ 1 組織だけ
   │    → そのシャードを丸ごと戻すと、**無関係な組織の当日ぶんも消える**
   │    → 復元先を新しい D1 にして、対象組織の行だけを移す（§2.4）
   │
   └─ シャード全体
        → そのまま戻す（§2.3）
```

**この判断を飛ばさないこと。** 1 組織のために 15 組織のデータを消した、が
最も起きやすい事故。

### 2.3 シャードごと戻す

```bash
# 1. 戻せる時点を確認する
pnpm --filter @pk/web exec wrangler d1 time-travel info \
  proofkeeping-shard-07 --env production

# 2. 復元（時刻指定）
pnpm --filter @pk/web exec wrangler d1 time-travel restore \
  proofkeeping-shard-07 --timestamp 2026-08-15T02:00:00Z --env production
```

復元後に必ず確認する。

1. `GET /api/health` で `schemaVersionConsistent: true`。
   **戻した時点のスキーマが現在のコードと合わない場合がある。**
   合わなければ `pnpm db:migrate --env production` を再適用する。
2. 対象組織で読み取りと書き込みを 1 件ずつ試す。
3. **戻した時点以降の記録は失われている。** 顧客へ、
   どの時点まで戻したかを伝える。清掃の記録は現場が覚えている場合がある。

### 2.4 1 組織だけ戻す

1. 復元先として**新しい D1 データベース**を用意する（本番の binding には繋がない）。
2. そこへ Time Travel で復元する。
3. 対象組織の行だけを取り出し、本番のシャードへ入れ直す。
   **`pnpm shards:move` の `--copy` は「組織単位でコピーする」実装なので
   流用できる。** 移送先を復元用 DB からのコピー元として使う。
4. 行数とチェックサムを照合する（`--verify`）。
5. 復元用の D1 を削除する。

**手順 3 で他の組織の行を持ち込まないこと。** コピーは
`organizationId` で絞る実装になっている。手で SQL を書かない。

## 3. R2 — バージョニング

### 3.1 誤削除からの復元

R2 はバージョニングが有効で、**削除は「削除マーカーを置く」動作**。
実体は 30 日残る。

```bash
# 1. 対象キーのバージョンを一覧する
pnpm --filter @pk/web exec wrangler r2 object list pk-photos \
  --prefix "photos/<orgId>/<propertyId>/" --env production

# 2. 削除マーカーより前のバージョンを取得して置き直す
```

キーの形は決まっている。

```
photos/{orgId}/{propertyId}/{businessDate}/{taskId}/{photoId}.jpg
```

**業務日で絞れる。** 「いつの写真が消えたか」が分かれば範囲を狭められる。

### 3.2 保持期限のバッチが消した場合

これは**誤削除ではない**（`PHOTO_RETENTION`）。仕様どおりの動作で、
削除の 30 日前に管理者へ通知している。

```
問い合わせが来た
   │
   ├─ 通知が届いていたか（notification の記録）
   │
   ├─ 保持期間の延長が必要か
   │    → organization.photoRetentionMonths を延ばす
   │       **短くする方向には戻せない**（版数の既定が下限）
   │       ※ 延長する画面が無い（OPEN_QUESTIONS #098）。現状は DB を直接触る
   │
   └─ 消えた写真を戻すか
        → R2 のバージョニングで 30 日以内なら戻せる
        → **D1 の行は先に消えている。** 行を戻さないと画面から辿れない。
           §2 の D1 復元が先
```

**D1 の行を先に消し、R2 の実体を後に消す**設計になっている。
戻すときは**逆順**（D1 → R2）。

### 3.3 帳票 PDF が消えた場合

**発行済み帳票の PDF は削除しない設計。** 消えているなら異例の事態。

1. R2 のバージョニングから戻す。
2. 戻せない場合、`payloadSha256` と帳票の行は D1 に残っているので、
   **同じ内容で PDF を再生成できる。** 番号は再採番しない。
3. 再生成した PDF の `pdfSha256` が元と一致しない場合がある
   （フォントや生成日時の埋め込み）。**その事実を監査ログに残す。**

## 4. KV

セッションのみ。**消失しても再ログインで復旧する。** 復元手段は用意しない。

**例外は `SHARD_MAP`。** ここが消えると、移送済みの組織のデータが
複数シャードに分裂する（`shard-move.md` ④）。

```
SHARD_MAP のキーが消えている可能性がある
   │
   ├─ 移送の記録（この文書の §6 の履歴）から、対象組織と移送先を引く
   ├─ wrangler kv key put で書き直す（**TTL を付けない**）
   └─ 分裂していた期間に書かれた行を、移送先へ寄せる
```

**移送の履歴を残していないと復旧できない。** §6 に必ず追記すること。
