# 業務の流れの通し確認（staging / seed01）

**2 日構成。** 1 日目に設定から清掃・検査まで、2 日目に締めと帳票を通す。
**1 日で終わらない理由は請求にある**（後述の §0.2）。

- 対象環境: **staging のみ**（<https://pk-staging.ukh816-account.workers.dev>）
- 前提データ: **seed01**（`POST /api/v1/dev/seed` で投入済みのもの）
- 所要時間の目安: **1 日目 約 100 分 / 2 日目 約 55 分**

この手順書は「25 段階の業務の流れが最初から最後まで通るか」を人が手で
確かめるためのもの。**画面と API から動かす。** DB へ直接入れない
（行が保存できることしか確かめられず、画面と画面のつなぎ目が通るかを
確認できないため）。

> 測定は実データでなければ意味がない。ここで作る差異は、稼働予定を

### 0.2 なぜ 2 日構成なのか（請求の期間の決まり方）

**請求期間はリクエストで指定できない。** 取引先の `closingDay`（締め日）
から `closedPeriodAsOf()` が「直近に締まった期間」を導く
（`packages/billing/src/period.ts`）。期間を指定できると、締め日と
合わない範囲の請求書が作れてしまうため、意図的にそうしてある。

```
closedPeriodAsOf(closingDay, onDate)
  当月の締め日が onDate より前  → その締め日までが直近の期間
  そうでなければ                → 前月の締め日までが直近の期間
```

つまり **「締め日」を過ぎていないと、その日の清掃実績を含む期間が
起票できない。** そこで最短の通し方はこうなる。

1. **1 日目**: 取引先の締め日を**前日の日付**に設定し、清掃〜検査まで通す
2. **2 日目**: 期間を起票する。1 日目の実績が「直近に締まった期間」に入る

> 例: 1 日目が 9 月 10 日なら、締め日を **9 日**にする。
> 2 日目（9 月 11 日）に起票すると、期間は **8/10〜9/9** になる。
> **1 日目の清掃（9/10）はこの期間に入らない。**
> 1 日目の実績を請求に載せたい場合は、締め日を **10 日**にして
> 2 日目に起票する（期間は 8/11〜9/10 になる）。**こちらを推奨。**

### 0.4 役割を切り替える場所（**ログインし直しが要る箇所**）

## 2 日目

### 段階 21 — 差異照合  ⏱ 約 15 分  ★ログインし直し（管理者）

`/login` で管理者（`seed01` / `0001` / `testpass-01`）に入る。

**(a) 稼働記録（A 系統）を入れる — 画面が無いので API を使う**

差異を実際に出すために入れる。**入れなくても照合は完走する**（差異 0 件）。

```
POST /api/v1/occupancy/import/csv
Content-Type: application/json

{"propertyId":"<施設ID>","businessDate":"YYYY-MM-DD","csv":"room_number,is_occupied,guest_count\n101,1,2\n102,0,0\n"}
```

- **セッション Cookie が要る**（ブラウザの開発者ツールから叩くのが早い）。
- 必須列は `room_number` と `is_occupied` の 2 つ。
- **`is_occupied` が空欄・不明な行は取り込まれない**（空室と決めつけない）。
- **差異を出したい場合**: 清掃して使用痕跡のある部屋を `is_occupied=0`
  にすると R001 が立つ。

**(b) 照合を起動する — 画面からは起動できない**

```
POST /api/v1/reconciliation/runs
Content-Type: application/json

{"propertyId":"<施設ID>","businessDate":"YYYY-MM-DD"}
```

- **権限は OWNER / ORG_ADMIN のみ**（他は 404）。
- **応答は 202。** Queue に載るだけなので、結果は少し待つ。
- 未来の日付・90 日より前は断られる。
- **UI から起動する手段は無い**（夜間 02:00 JST の cron か、この API）。

**(c) 結果を見る**

1. `/app/audit/findings` を開く。
   - **確認**: 画面が開く（**差異 0 件でも開くのが正**）。
   - 差異があれば一覧に出る。「次の 1 件」から詳細（W-07）へ。
2. **確認**: 詳細に 3 系統（稼働記録・観察記録・入室記録）の枠が出る。

### 段階 22 — 日報  ⏱ 約 10 分

**日報は日締めの 10 分後に自動で作られる**（`*/10` の cron）。
待たずに作るには API を使う。

```
POST /api/v1/reports/daily/generate
{"propertyId":"<施設ID>","businessDate":"YYYY-MM-DD"}
```

- **応答は 202。** PDF は Queue が作る。
- 一覧: `GET /api/v1/reports/daily?propertyId=<施設ID>`
- ダウンロード: `GET /api/v1/reports/daily/{id}/download`（15 分有効の URL）

**確認**: PDF が作られ、**日本語が字として出ている**こと。

> **W-08（日報一覧の画面）はまだ無い。** API から確かめる。
> 書体はデプロイに同梱されるので、**配置の作業は要らない**（DECISIONS #256）。
> **staging で日報を 1 通作るのが、書体がアセットから読めることの初めての確認になる。**

### 段階 23 — 月報  ⏱ 約 5 分

1. `/app/p/{propertyId}/report` を開く（サイドバー「月次レポート」）。
   - 既定は**前月**。`?month=YYYY-MM` で指定できる。
2. **確認**: 画面が開き、日本語で表示される。
3. **確認**: ブラウザの印刷でレイアウトが崩れない。

> **月報は HTML でブラウザ印刷する。PDF も採番も持たない**（#196）。

### 段階 24 — 請求書  ⏱ 約 20 分

**(a) 前提を揃える**

1. `/app/settings/tax`（事業者・税務設定）
   - **確認**: 法人名が入っている。**未設定だと発行が 409 で断られる。**
   - 登録番号は未設定でもよい（その場合「適格請求書ではありません」と出る）。
2. `/app/settings/counterparties`（取引先と料金）
   - 取引先を 1 件作る。**請求先メールアドレスを必ず入れる**（段階 25 で使う）。
   - **締め日を §0.2 のとおりに決める**（1 日目の日付にすると、その日の
     実績が期間に入る）。
   - **料金設定を最低 1 行作る。**
     - **施設を指定しない行を 1 つ作ると、全施設が対象になる。**
     - **料金設定が 1 行も無いと、対象施設が 0 件になり明細も 0 件になる。**

**(b) 期間を起票する（cron を待たない）**

```
POST /api/v1/billing-periods?counterpartyId=<取引先ID>
```

- **期間はリクエストで指定できない**（§0.2）。締め日から導かれる。
- 応答に `periodFrom` / `periodTo` が入る。**ここで期間を確認する。**

**(c) 集計 → 合意**

1. `/app/billing-periods` を開く。
   - **確認**: 起票した期間が出ている。
2. 集計する（`OPEN` → `REVIEWING`）。
   - 画面に無ければ `POST /api/v1/billing-periods/{id}/aggregate`。
3. 明細を確認し、**合意**する（`REVIEWING` → `AGREED`）。
   - **確認**: 明細に清掃の件数と金額が出ている。
   - **単価が引けなかった明細には警告が出る**（0 円で計上される）。

**(d) 発行する — 画面にボタンが無いので API を使う**

```
POST /api/v1/invoices/issue-and-send
{"billingPeriodId":"<期間ID>"}
```

- **`AGREED` でないと 409。**
- 採番され（`INV-2026-0001`）、請求書が作られ、**PDF と送付が Queue に載る。**
- 発行と同時に**送付も投入される**（段階 25 はこれで完了する）。

**(e) 確認**

1. `/app/billing` を開く。
   - **確認**: 請求書が一覧に出る。文書番号・金額・状態。
2. `/app/billing/{invoiceId}` を開く。
   - **確認**: 明細・税率ごとの内訳・PDF へのリンク。
   - **確認**: PDF の**日本語が字として出ている**こと。

### 段階 25 — 帳票の送付  ⏱ 約 5 分

**(d) で送付まで投入済み。** ここでは着いたかを確かめる。

1. 取引先の請求先メールアドレスの受信箱を見る。
   - **確認**: 件名とリンクのメールが届く（**PDF は添付されない**。
     本文のリンクから開く）。
2. 届かない場合の切り分け:
   - 宛先が空 → **投入そのものが行われない**（発行時の写しから宛先を読む）
   - `SMTP_PASSWORD` 未登録 → 送信が失敗して再送に回る
   - **配達・開封・バウンスは分からない**（SMTP に webhook が無い / #118）
3. 領収書も試す場合: `/app/billing/{invoiceId}` から**発行と送付ができる**
   （請求書と違い、こちらは画面にボタンがある）。

### 片付け（テストデータの消し方）

**seed のデータを消す手順は用意していない。** `staging-bootstrap.yml` の
`reset-db` は「業務データが 1 行でもあれば中止する」ので、この確認を
行った後は使えない。

staging を白紙に戻したい場合は、**この確認で作ったものだけを画面から
無効化する**（削除ではない）:

- 検査担当（`2001`）→ `/app/settings/members` から無効化
- 取引先と料金設定 → `/app/settings/counterparties` から無効化・期間クローズ
- 検査ポリシー → `/app/settings/inspection` で「検査を行わない」へ戻す
- 稼働予定・タスク・観察記録・検査・差異・帳票 → **消さない**
  （**発行済みの帳票は消せない。** 電子帳簿保存法の要請で、訂正は
  赤伝＋再発行。`docs/runbook/` の該当章を見ること）

> **見分け方**: この確認で作ったものはすべて組織 `seed01` に属し、
> ID が `seed01__` で始まる。施設名は「サンプル」で始まる。
