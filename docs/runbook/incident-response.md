# 障害対応手順

**版**: v1.0（2026-08-15）
**対象**: 社内（オンコール担当）
**仕様**: docs/PK-SPEC-P7.md §5.2〜§5.4

**症状から入る。原因から入らない。**
連絡を受けた時点で分かっているのは症状だけで、原因は分かっていない。

---

## 0. 最初の 5 分

```
        連絡を受ける / アラートで気づく
                    │
                    ▼
        ┌───────────────────────────┐
        │ 1. GET /api/health を見る  │
        └─────────────┬─────────────┘
                      │
        ┌─────────────┴─────────────┐
        │                           │
   state = "degraded"          state = "ok"
        │                           │
        ▼                           ▼
  §1 全体の障害へ            §2 症状別へ
```

`/api/health` は認証不要。**返るのは件数と真偽だけで、
どの番号のシャードが落ちているかは含まない**（内部構成を語らせないため）。
番号が要るときは `pnpm shards:usage --env production` を使う。

```json
{
  "state": "ok",
  "shards": { "state": "ok", "expected": 16, "declared": 16,
              "reachable": 16, "schemaVersionConsistent": true },
  "storage": "ok", "cache": "ok", "queues": "ok"
}
```

### 優先度（§5.2）

**すべてを同時に直そうとしない。** 下から諦める。

| 優先度 | 機能 | 障害時の扱い |
|---|---|---|
| 1 | 清掃タスクの参照・開始・完了 | **何があっても維持する** |
| 2 | 写真アップロード | 端末のキューで吸収 |
| 3 | 検査 | 一時的に「検査なし」へ寄せてよい |
| 4 | 客室ボード | 更新頻度を落とす |
| 5 | 照合バッチ | 遅延して実行 |
| 6 | PDF 生成 | キューに滞留させる |
| 7 | 外部連携 | 停止して手動 CSV へ |

**優先度で機能を止める実行時のコードは書いていない**（DECISIONS #161）。
この表は「壊れたときに人がどこから諦めるか」の順序であって、
平常時に分岐する仕組みではない。

### 稼働率の目標

全体 99.5% / 月、**清掃時間帯（06:00–20:00）は 99.9% / 月。**
時間帯によって同じ停止時間の重みが違う。朝の 10 分は夜の 10 分より重い。

## 1. 全体の障害

### 1.1 `shards.reachable < expected`（シャードに届かない）

```
届かないシャードがある
   │
   ├─ Cloudflare のステータスを確認（D1 の広域障害か）
   │     広域障害 → 顧客告知へ。復旧を待つ。手を出さない
   │
   └─ 局所 → pnpm shards:usage --env production で番号を特定
         │
         ├─ 使用率が 85% 超 → §4 逼迫。移送を検討（shard-move.md）
         └─ 使用率は正常 → binding の設定変更が入っていないか
                             直近のデプロイを疑う（deploy.md §5 ロールバック）
```

**影響は「その番号のシャードに載っている組織だけ」。** 全顧客ではない。
どの組織が該当するかは `resolveShard()` の規則から求める。

### 1.2 `schemaVersionConsistent: false`（マイグレーションが途中で止まった）

**これは最も危険な状態。** シャードごとにスキーマが違うため、
同じ API が組織によって成功したり失敗したりする。

```
1. pnpm db:migrate --env production --check
     → 未適用のシャード番号が出る
2. 直前のデプロイのログで、どのシャードで中止したかを確認
3. 未適用のシャードへ適用を再開する
4. /api/health で consistent: true を確認
```

**書き込み系 API を 503 にする middleware は未実装**（§5.3 MUST / P0-20 の
未達分）。現時点では**人が気づいて止める**しかない。
不一致が長引く場合は、旧スキーマでも動く状態へ**戻す**方が安全
（`deploy.md` §5）。

> **4xx で塞がないこと。** 4xx は端末側のキューが `GIVE_UP` と判定し、
> 未送信の記録が捨てられる。塞ぐなら 503。

### 1.3 `storage: "degraded"`（R2 に届かない）

写真の表示と PDF の保存が止まる。**優先度 2 と 6。**
清掃タスクの完了は写真が無くても通る設定なら続行できる。

- 写真は端末のキューに残る。**復旧後に自動送信される。**
- PDF はキューに滞留する。**生成をやり直す必要はない。**

### 1.4 `cache: "degraded"`（KV に届かない）

**ログインができなくなる。** セッションの実体が KV にあるため。
既にログイン済みの端末は、セッションの読み取りで落ちる。

- **ここは縮退できない。** Cloudflare 側の復旧を待つ。
- 顧客告知の対象（優先度 1 に影響する）。

## 2. 症状別

### 2.1 「現場でタスクが出ない」

```
特定の 1 人か、その施設の全員か
   │
   ├─ 1 人だけ
   │    ├─ 担当施設の割当がされているか（設定漏れ）
   │    ├─ ロールが CLEANER のままか（変更直後は次の操作から反映）
   │    └─ その日のタスクが配分されているか（W-04）
   │
   └─ 施設の全員
        ├─ その業務日のタスクが生成されているか
        │    → 02:00 JST の cron が走ったか。走っていなければ手動実行
        ├─ 客室状況（roomPlan）が登録されているか
        │    → 未登録だと生成対象が無い。**これが最も多い**
        └─ 施設の日締め時刻を変更していないか
             → 業務日の境界が動く。「昨日の分」として出ていないか
```

### 2.2 「送信されない・未送信が溜まる」

端末上部のバーに件数が出る。**24 時間以上で赤。**

```
赤いバーが出ている
   │
   ├─ その端末だけ → ブラウザを開き直す（flush の契機を作る）
   │                   Safari のタブは 7 日で storage が消える。
   │                   **消えた記録は戻らない。**
   │
   └─ 複数端末 → §1 全体の障害へ。API が 5xx を返していないか
                  **409 は正常。** 処理済みとして成功扱いで消える
```

### 2.3 「写真が上がらない」

- 1 枚 500KB を超えていないか（端末側で縮小している。縮小前に落ちていないか）
- R2 の状態（§1.3）
- レート制限（60 req/分/ユーザー）に当たっていないか

**優先度 2。** 復旧を待ってよい。清掃の完了は止めない。

### 2.4 「PDF が出ない」

```
PDF が出ない
   │
   ├─ 和文フォントが配置されているか
   │    → **未配置なら 1 枚も作られない。** 最初にここを見る
   ├─ pk-pdf-generation キューが作られているか（4 環境ぶん）
   ├─ コンシューマがエラーで止まっていないか（Workers のログ）
   └─ 単に順番待ちか → 数分待つ。**優先度 6。滞留は正常な縮退**
```

### 2.5 「メールが届かない」

- Resend の送信ログを見る。**送っているのに届かないのか、送っていないのか。**
- `RESEND_WEBHOOK_SECRET` が未設定だと配信結果の受信が 401 になる。
  送信自体は成功しているのに「届いたか分からない」状態になる。
- 静音時間（22:00–07:00）に当たっていないか。**仕様どおりの停止。**

**通知が届かなくても全業務は成立する。** ここは優先度が低い。

### 2.6 「差異レポートが出ない・古い」

```
照合が走っていない
   │
   ├─ 02:00 JST の cron が発火したか
   ├─ ReconciliationLock が解放されているか（二重起動の防止で待っている）
   ├─ 稼働記録（① 系統）が入っているか
   │    → 未接続なら R006 だけが立つ。**これは仕様どおり**
   └─ Audit モジュールが有効か（402 が返っていないか）
```

**優先度 5。遅延して実行してよい。** 当日中に追いつけばよい。

### 2.7 「請求書が発行できない」

- 締め（`BillingPeriod`）がロックされているか。**ロック前は確定できない。**
- 料金設定が無いタスクは**単価 0 円の明細**として載る。除外していない。
  画面に警告が出ているはず。
- 採番は `DocumentSequencer` 経由のみ。DO に届かない場合は §1 へ。

### 2.8 「全体が遅い」

```
遅い
   │
   ├─ 特定の施設だけ → 客室数（100 室超の盤面）。§4.1 の目標は 800ms
   ├─ 特定の時間帯だけ → 朝のピーク（09:00–10:00）。§4.2 シナリオ A
   └─ 全体 → pnpm shards:usage で偏りを見る。1 シャードに大口が集中していないか
```

## 3. 優先度の判定と告知

| 優先度 | 定義 | 初回応答 | 解決目標 | 告知 |
|---|---|---|---|---|
| P1 | 清掃業務が止まる | 1 時間 | 4 時間 | **ステータスページで告知する** |
| P2 | 一部機能が使えない | 4 時間 | 1 営業日 | 問い合わせに応じて |
| P3 | 不具合だが回避可能 | 1 営業日 | 5 営業日 | 不要 |
| P4 | 質問・要望 | 2 営業日 | — | 不要 |

**P1 は 24 時間受付。** 判定に迷ったら P1 に寄せる。
清掃時間帯（06:00–20:00）は 1 段階上げて扱う。

### 発見から告知まで（§5.4）

```
発見（Workers のログ / 顧客からの連絡）
   → 5 分以内に社内チャットへ共有
   → 優先度 1 の機能に影響するなら顧客へステータスページで告知
```

**Sentry への集約はまだ実装していない**（P0-20 の未達分。
採用可否が未決 / OPEN_QUESTIONS #030）。
現時点で気づける経路は **Workers のログ**と**顧客からの連絡**の 2 つだけ。
**アラートで先に気づける前提で運用しないこと。**

## 4. シャードの逼迫

```
pnpm shards:usage --env production
```

| 使用率 | レベル | 行動 |
|---|---|---|
| 〜60% | ok | なし |
| 60〜75% | 注意 | 週次で見る |
| 75〜85% | 警告 | 移送の計画を立てる |
| 85%〜 | 危険 | **移送する**（`shard-move.md`） |

D1 の上限は 10GB / データベース。
**測れていない使用率を `ok` に混ぜない**（DECISIONS #158）。
値が取れなかったシャードは「不明」として出る。

## 5. 記録

対応が終わったら、次を残す。

1. 症状（顧客の言葉のまま）
2. 影響範囲（組織・施設・時間帯・優先度）
3. 原因
4. 復旧までに行ったこと
5. **この手順書のどこが足りなかったか**

5 を書かない振り返りは意味が無い。
**手順書だけで対応できたかどうかが、この文書の合否**（P7-14）。
