## 4. エスカレーション

```
        連絡・アラート
              │
              ▼
      ┌────────────────┐
      │ 一次受け        │  /api/health を見る（incident-response.md §0）
      └───────┬────────┘
              │
      ┌───────┴────────────────────────────┐
      │                                    │
  手順書で対応できる                手順書に無い / 30 分で切り分かない
      │                                    │
      ▼                                    ▼
  対応 → 記録                    ┌────────────────┐
                                 │ 二次（技術）    │
                                 └───────┬────────┘
                                         │
                          ┌──────────────┴──────────────┐
                          │                             │
                  優先度 1 に影響しない          優先度 1 に影響する
                          │                             │
                          ▼                             ▼
                     対応 → 記録              ┌────────────────────┐
                                              │ 三次                │
                                              │ + 顧客告知（5 分以内）│
                                              └────────────────────┘
```

**30 分で切り分かなければ上げる。** 抱え込まない。
**優先度 1 に影響するなら、原因が分かる前に告知する。**
「原因が分かってから知らせる」は、現場が止まっている時間を伸ばすだけ。

## 5. 顧客への告知（§5.4）

```
発見
  → 5 分以内に社内チャットへ共有
  → 優先度 1 の機能に影響するなら、ステータスページへ掲出
```

告知に書くこと。

1. **何ができないか**（原因ではなく症状）
2. 影響範囲（全体か、一部の施設か）
3. 現場が今できること（例: そのまま記録を続けてよい。復帰後に自動送信される）
4. 次の更新予定時刻

**「原因を調査中です」だけを出さない。** 3 が最も重要。
清掃タスクの参照・開始・完了は端末側のキューで受けるので、
多くの障害では**現場は作業を続けられる。** それを伝える。
