**版**: v1.0（2026-08-15）
**対象**: 社内（運用者・監査対応）／税務調査時の提示書類
**仕様**: docs/PK-SPEC-P7.md §7.2 / task: docs/tasks/P7-16.md

**この文書は電子帳簿保存法の「システム関係書類等の備付け」に応える。**
電子取引（PDF の請求書・領収書をメールで授受する行為）の保存要件のうち、
書類として備え付けるべきものを 1 か所から辿れる形にしてある。

## 2. システムの目的と範囲

ProofKeeping は、宿泊施設の清掃業務の記録を残し、
その記録を根拠に請求書・領収書を発行するシステムである。

電子帳簿保存法の対象になるのは、このうち**帳票の発行・保存・授受**にあたる部分。

| 対象 | 帳票 |
|---|---|
| 電子取引（発行） | 請求書 PDF・領収書 PDF をメールで送付する |
| 電子取引（授受の記録） | 送付の事実を `document_delivery` に記録する |
| 対象外 | 清掃の記録・写真・検査結果（帳簿書類ではない。ただし請求の根拠として同じ保存要件で扱う） |

---

## 3. 記録の作成から保存までの流れ

```
① 清掃タスクの完了・検査合格          （現場・検査担当）
      ↓  記録は追記のみ。上書きしない
② 月次締め（BillingPeriod をロック）  （毎月 1 日 04:00 JST / 自動）
      ↓
③ 請求書の下書きを作る                （管理者）
      ↓
④ 確定
      ├ DocumentSequencer で採番（INV-{西暦}-{連番4桁}）
      ├ 明細・税区分を INSERT
      ├ 発行元・取引先の情報を JSON で固定（スナップショット）
      ├ payloadSha256 を計算
      └ status = CONFIRMED          ← ここまで 1 トランザクション
      ↓
⑤ PDF 生成（Queue: pdf-generation）
      ├ pdfSha256 を計算
      └ R2（DOCUMENTS バケット）へ保存
      ↓
⑥ 送付（Queue: notification → Lark Mail SMTP）
      └ DocumentDelivery に送付先・時刻・結果を記録
      ↓
⑦ status = SENT／AuditLog へ記録
```

**PDF の生成をリクエストハンドラで行わない。** Queue コンシューマ内のみ。

## 4. 保存要件への対応

### 4.1 真実性の確保

ProofKeeping は**「訂正・削除の履歴が残るシステム」方式**を採る。
**外部タイムスタンプは導入していない。** そのため以下をすべて満たす。

| 要件 | 実装 |
|---|---|
| 発行済み帳票を物理削除しない | 削除の API を作らない。リポジトリ層にも `delete` を置かない |
| 訂正の履歴が残る | 訂正は赤伝（マイナス伝票）＋再発行。元の行は残す |
| 元の PDF を保持する | R2 に残し、閲覧可能なまま維持する |
| 全操作の記録 | `AuditLog`（発行・訂正・送付・エクスポート） |
| 改変の検出 | `payloadSha256` と `pdfSha256` |

### 4.2 可視性の確保

**取引年月日・取引金額・取引先**の 3 項目で検索できること。

そのため帳票テーブルに次を**非正規化して保持し、索引を張っている。**

```ts
issueDate: text("issue_date").notNull(),         // YYYY-MM-DD
totalAmount: integer("total_amount").notNull(),  // 税込
counterpartyName: text("counterparty_name").notNull(),
```

参照元のマスタを変更しても、**過去の帳票の記載は変わらない**
（発行時にスナップショットで固定しているため）。

### 4.3 適格請求書の 6 要件

発行事業者の名称と登録番号（T + 13 桁）／取引年月日／取引内容／
税率ごとの対価の合計と適用税率／税率ごとの消費税額等／交付先の名称。

登録番号が未設定の場合は「適格請求書ではありません」と明記し、
`isQualifiedInvoice = false` を記録する。

### 4.4 金額の計算

- **浮動小数点を使わない。すべて整数（円）。**
- 明細行の `amount = quantity × unitPrice`（整数演算）。
- **端数処理は税率ごとに 1 回だけ。** 明細行ごとには行わない。
- 端数処理の方式は取引先ごとの設定（FLOOR / CEIL / ROUND）。

### 4.5 電子領収書と印紙税

PDF で発行・送付する領収書は紙の文書の交付にあたらないため
課税文書に該当せず、**収入印紙は不要**（5 万円超でも同じ）。
テンプレートに印紙貼付欄を設けず、その旨を固定表示している。

## 5. 事務手続（電子計算機処理に関する事務手続を明らかにした書類）

### 5.1 責任と分担

| 役割 | 担当 | 内容 |
|---|---|---|
| 帳票の発行 | 顧客組織のオーナー / 運営管理者 | 締め・確定・送付 |
| システムの運用 | 株式会社ステック | デプロイ・バックアップ・障害対応 |
| 保存データの管理 | 株式会社ステック | R2・D1 の保持と復旧 |

### 5.2 入力の手続

1. 清掃タスクの記録は**当日中**に現場が入力する。
   電波が無い場合は端末に保持し、復帰時に自動送信する。
2. 月次締めは翌月 1 日 04:00 JST に自動で起票する。
3. 締め後の実績の追加は、**赤伝と再発行**で行う。締め済みの期間を直接編集しない。

### 5.3 訂正・削除の手続

**発行済み帳票の削除はできない。** 訂正が必要な場合は次の順で行う。

1. 元の請求書に対してマイナス伝票（赤伝）を発行する。
2. 正しい内容で新しい請求書を発行する。
3. 番号は再利用しない。**取消した番号は欠番のまま残す。**
4. 1〜3 のすべてが `AuditLog` に残る。

### 5.4 保存期間

| 対象 | 期間 | 備考 |
|---|---|---|
| 帳票（請求書・領収書）と PDF | 削除しない | 電子取引の保存要件 |
| 清掃・検査・観察の記録 | 年次で R2 へ退避。閲覧は復元して行う | 退避は削除ではない |
| 写真 | 既定 6 か月 / 上位プラン 13 か月 / 最大 36 か月 | 削除 30 日前に通知 |
| 同期ログ | 7 日 | 個人情報はマスク |

### 5.5 障害時の取扱い

障害で入力できない場合も、**清掃タスクの参照・開始・完了は端末側の
キューで受ける**（縮退運転の優先度 1）。復旧後に自動送信される。

帳票の発行が滞った場合、締め自体は月次バッチが起票済みであるため、
復旧後に同じ期間に対して発行できる。**同じ期間を二重に発行しない**
（`BillingPeriod` のロックと `Idempotency-Key` による）。

障害対応の手順は `docs/runbook/incident-response.md`、
復旧の手順は `docs/runbook/recovery.md`。

## 6. データの所在

| 種類 | 保存先 |
|---|---|
| 業務データ | Cloudflare D1（16 シャード） |
| 写真・帳票 PDF・証跡 ZIP・退避データ | Cloudflare R2 |
| セッション・レート制限・接続情報 | Cloudflare Workers KV |
| 実行環境 | Cloudflare Workers |

いずれも Cloudflare のマネージドサービス上にある。
構成の詳細は `docs/runbook/architecture.md`。

---

## 7. 保存しないデータ

**宿泊者の氏名・連絡先・住所・パスポート情報・カード情報を保存しない。**
稼働の照合には人数と予約参照番号のみを用いる。
忘れ物の所有者情報も保存しない。

この方針は設計上の選択であり、**該当する列がスキーマに 1 つも無いことを
CI で機械的に確かめている**（`packages/db/src/schema/guestPii.spec.ts`）。
